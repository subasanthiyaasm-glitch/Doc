OpenCode

OpenCode — AI Coding Agent

Terminal-based AI coding assistant. Works with local & cloud models. Executes tasks autonomously in your shell.
CLI Commands
opencode          # Start interactive session
opencode --model gpt-4  # Choose model
opencode --help       # Show help
opencode --version    # Show version
/help                      # In-session help
/model claude-sonnet   # Switch model mid-session
/clear                     # Clear conversation
/exit                      # Exit session
/task "refactor X"     # Run autonomous task
Pro Tips
⚡ Use Ctrl+C to interrupt a long response
🔁 /model switches models without restarting
📎 Drag & drop files into terminal to attach context
🌐 Use webfetch skill to scrape live URLs
🧩 Load skills with the skill tool
Supported Models
gpt-4o          # OpenAI
gpt-4o-mini      # OpenAI (fast)
claude-sonnet-4  # Anthropic
claude-haiku     # Anthropic (fast)
gemini-2.5-pro   # Google
gemini-2.5-flash # Google (fast)
deepseek         # DeepSeek
llama-3.1        # Meta (local)
QwQ-32B          # Qwen (local)
Key Concepts
Skills — Specialized instruction files loaded per-task
Sub-agents — Delegate complex/multi-step work to child agents
Tools — Bash, file read/write, search, web fetch, browser automation
Permissions — Granular allow/deny per command or tool

LLM & AI Agents

An LLM is a next-token prediction function built on the Transformer architecture. An Agent is an LLM + autonomous loop: perceive → reason → act → observe → repeat.
Transformer Architecture
# "Attention Is All You Need" (Vaswani 2017)
# Every major LLM: GPT, Claude, Gemini, Llama

# Core pipeline:
1. Tokenize    text → token IDs (BPE algorithm)
2. Embed       token IDs → high-dim vectors
3. + Position  add positional encoding
4. Attention   each token looks at all others
5. FFN         process each position independently
6. Repeat ×N   N layers (more = deeper reasoning)
7. Softmax     → probability distribution → next token

# Self-Attention (simplified):
# Q = Query, K = Key, V = Value
# attn = softmax(Q·Kᵀ / √d) · V
▶ Tokenization
"ServiceDesk" → ["Service","Desk"]
"hello" → [" hello"] (space included)
Rule: 1 token ≈ 4 chars ≈ 0.75 words
Why output costs more: generated serially (one full forward pass per token) vs input processed in parallel.
Prompt Engineering
# System prompt sets persona & constraints
"You are a senior Python developer."

# Chain-of-thought (CoT)
"Let's think step by step"
→ forces intermediate reasoning tokens

# Few-shot: show examples first
"Q: 2+2? A: 4
 Q: 3+5? A: 8
 Q: 7+1? A:"

# Temperature controls randomness
temp=0.0  → deterministic (SQL, extraction)
temp=0.7  → balanced (general use)
temp=1.5  → creative (brainstorming)

# XML tags structure input (Claude)
<task>Refactor this code</task>
<code>def foo(): ...</code>
▶ RLHF Pipeline
Stage 1: Pretrain — next-token prediction
Stage 2: SFT — human-written examples
Stage 3: Reward Model — human preference pairs
Stage 4: RL (PPO/DPO) — optimize for reward
Alternatives: DPO (simpler), Constitutional AI (self-critique), RLAIF (AI-as-rater)
Tokens & Billing
# Everything is denominated in tokens
Context window — max tokens per call (input + output)
Input tokens   — system prompt + history + message + tools
Output tokens  — model generates, one at a time
Pricing        — per million tokens, I/O priced separately

# Output costs 3–5× more than input:
Input  tokens → processed in parallel   → cheaper
Output tokens → generated one by one   → expensive

# In an agent loop, context grows every turn:
Turn 1:  system (2K) + msg (50)                = ~2,050
Turn 4:  system (2K) + history (3K) + tools (1K)  = ~6,000
Turn 10: same + accumulated tool results       = ~20,000+
▶ Why Billing Uses Tokens
Per API call → "flat taxi fare" ✗
Per memory → "charge for whole DC" ✗
Per token → "pay for work done" ✓
GPU cost scales linearly with tokens — each output token = one full forward pass.
What Makes Models Different
# Ordered by impact (training data is LEAST important)

1. Architecture  (biggest)
   Layers, head count, MoE vs dense
   Positional encoding (RoPE, ALiBi, learned)
   → Changes what the model can do

2. Scale
   Parameter count, training FLOPs
   Chinchilla laws: double compute = predictable gain
   A 7B vs 70B model on identical data → categorically different

3. Training method
   Same data + different method = different model
   Pretraining objective, RLHF vs DPO vs CAI

4. Alignment & fine-tuning
   SFT on curated instruction-response pairs
   RLHF/DPO shapes tone, safety, verbosity

5. Training data  (least)
   Affects domain knowledge, NOT reasoning ability
   GPT-2 and GPT-4 share sources — gap is scale + method

LLM vs Agent
# LLM (stateless):
prompt → [LLM] → response    # one shot, stops

# Agent (autonomous loop):
goal → [LLM: what to do?]
         ↓
     [Tool executes]
         ↓
     [Result back to LLM]
         ↓
     [LLM: done or next step?]  # loops until done

# ReAct pattern:
Thought: I need to find the file
Action:  bash: find . -name "*.py"
Observation: found 3 files
Thought: Now read the main one...

# Agent memory types:
In-context     conversation window (fast, limited)
External       vector DB, SQL, files (RAG)
Working        scratch notes within a run
Long-term      persisted across runs

Local Inference — GGUF vs MLX
# GGUF — universal standard
Framework:  llama.cpp
Hardware:    Any CPU, optional GPU offload
Format:      Single .gguf file
Ecosystem:   Ollama, LM Studio, Jan
# Contains: weights + tokenizer vocab + metadata
# Does NOT contain: inference code or training data

# MLX — Apple Silicon native
Framework:   Apple MLX
Hardware:    M1/M2/M3/M4 only
Speed:       Faster on Mac (unified memory)
# CPU and GPU share same RAM → no copy overhead

# Quantization (same model, different precision):
Q8_0    8-bit   → near-lossless, large
Q4_K_M  4-bit   → sweet spot ✓
Q2_K    2-bit   → noticeable loss, tiny
▶ The .gguf Analogy
.gguf file = Docker image (passive data)
llama.cpp = Docker Engine (executor)
your prompt = docker run (triggers execution)
model in RAM = running container
Ollama library = Docker Hub
Key diff from Docker: Docker images contain code. .gguf contains only data — logic is in the runtime.
Efficiency & Modern Improvements
# Test-time compute (biggest current shift)
Let model think longer → dramatically better
o1, o3, Claude Fable: always-on reasoning traces
Same base model, 10× compute = solves harder problems

# Mixture of Experts (MoE)
Router activates 2–4 experts per token (out of dozens)
140B total params, 20B active per token
Quality of large model, cost of small one

# Efficiency techniques
Quantization:     32-bit → 4-bit weights (4–8× smaller)
Distillation:     Large model trains small model
Speculative decode: Small model drafts, large verifies

# Long context
Standard attention: O(n²) — double context = 4× compute
Fixes: sparse attention, ring attention, RoPE scaling
Gemini 1.5 Pro: 1M tokens

# Synthetic data
Strong models generate training data for weaker ones
Phi-3-mini ≈ GPT-3.5 quality from synthetic data
▶ Glossary
BPE — Byte Pair Encoding tokenizer
KV cache — stored attention, avoids recompute
DPO — Direct Preference Optimization
CAI — Constitutional AI (self-critique)
MoE — Mixture of Experts (sparse activation)
RAG — Retrieval-Augmented Generation
Autoregressive — one token at a time
Hallucination — plausible but wrong output
