How a Java web request flows

Your browser sends a request. The server picks the right Java code to run, that code reads or saves data in the database, and a response travels all the way back to your screen. Watch one request make the round trip:

Browser Server · routing Service Database Response
Server-Side

Servlet

A request hits the server (doGet / doPost); a response goes back.
HttpServletRequest / HttpServletResponse — Tomcat creates these objects automatically. Client sends request, server returns response. W3Schools →
HttpServlet.java
import java.io.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class MyServlet extends HttpServlet {

  protected void doGet(HttpServletRequest req,
      HttpServletResponse resp)
      throws IOException, ServletException {

    // Read request data
    String user = req.getParameter("user");

    // Set response content type
    resp.setContentType("text/html");

    // Write response
    PrintWriter out = resp.getWriter();
    out.println("<h1>Hello " + user + "</h1>");
  }

  protected void doPost(HttpServletRequest req,
      HttpServletResponse resp)
      throws IOException, ServletException {
    doGet(req, resp);
  }
}
▶ Lifecycle
Servlet Lifecycle
1. init() — called once at startup
2. service() — routes to doGet/doPost
3. destroy() — cleanup on shutdown
Request / Response
Client → Server: HttpServletRequest
Server → Client: HttpServletResponse
HTTP Methods
doGet() — URL parameters, bookmark-safe
doPost() — form body, secure for data
RequestDispatcher — forwards request/response to another servlet or JSP. Data is shared via request.setAttribute().
RequestDispatcher
// Servlet A — set data and forward
RequestDispatcher rd = req.getRequestDispatcher("targetServletURL");
req.setAttribute("n", 2);
rd.forward(req, resp);

// Servlet B — read forwarded data
int n = (Integer) req.getAttribute("n");

// sendRedirect() vs forward()
// forward  — server-side, same request
// redirect — client-side, new request
resp.sendRedirect("otherPage.jsp");
▶ Forward vs Redirect
forward()
Server-side transfer
Same request/response objects
URL stays the same
Use for internal dispatch
sendRedirect()
Client-side redirect (302)
New request/response created
URL changes in browser
Use for external navigation
HttpSession — stores data across multiple requests for the same user. Server maintains session state.
HttpSession
// Servlet 1 — store session data
HttpSession session = req.getSession();
session.setAttribute("n", 10);

// Servlet 2 — retrieve session data
HttpSession session = req.getSession();
int temp = (Integer) session.getAttribute("n");

// Delete session attribute
session.removeAttribute("n");

// Invalidate entire session
session.invalidate();
▶ Session Details
How it Works
1. getSession() creates/returns session
2. Session ID stored in cookie (JSESSIONID)
3. Server maps requests to sessions
Key Methods
getAttribute(name) — get value
setAttribute(name, val) — set value
removeAttribute(name) — remove value
invalidate() — destroy session
getId() — get session ID
Scope
Session — across requests (user-specific)
Request — within one request only
Application — shared by all users
Cookies — client-side storage. Data is sent back to server with every request. Use for lightweight preferences.
Cookies
// Servlet 1 — create and send cookie
Cookie cookie = new Cookie("n", "10");
cookie.setMaxAge(86400); // 24 hours
resp.addCookie(cookie);

// Servlet 2 — read cookies
Cookie[] cookies = req.getCookies();
for (Cookie c : cookies) {
  if (c.getName().equals("n")) {
    String temp = c.getValue();
  }
}
▶ Cookie vs Session
Cookies (Client)
Stored in browser
Sent with every request
Size limit ~4KB
User can disable/delete
Sessions (Server)
Stored on server
Referenced by session ID
No size limit
More secure (not exposed)
Cookie: remember me • Session: shopping cart
ServletContext vs ServletConfig — Context is application-wide (shared by all servlets), Config is servlet-specific.
web.xml Config
<!-- web.xml — application-wide params -->
<context-param>
  <param-name>dbPassword</param-name>
  <param-value>secret123</param-value>
</context-param>

<!-- Servlet-specific params -->
<servlet>
  <servlet-name>MyServlet</servlet-name>
  <init-param>
    <param-name>maxConnections</param-name>
    <param-value>100</param-value>
  </init-param>
</servlet>

// Java — reading params
String dbPass = getServletContext()
    .getInitParameter("dbPassword");

String maxConn = getServletConfig()
    .getInitParameter("maxConnections");
▶ Config Comparison
ServletContext
Shared across ALL servlets
Defined with <context-param>
Use for: DB config, app-wide settings
ServletConfig
Only for current servlet
Defined with <init-param>
Use for: servlet-specific settings
Both use getInitParameter(name)
Annotations vs web.xml — modern Servlet 3.0+ uses annotations, older versions use XML deployment descriptor.
Annotations vs XML
// Modern — Annotation (Servlet 3.0+)
@WebServlet("/myServlet")
public class MyServlet
    extends HttpServlet { ... }

// With init params
@WebServlet(
  name = "MyServlet",
  urlPatterns = {"/myServlet", "/alt"},
  initParams = {
    @WebInitParam(name="max", value="100")
  }
)

// Legacy — web.xml
<servlet>
  <servlet-name>MyServlet</servlet-name>
  <servlet-class>com.app.MyServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>MyServlet</servlet-name>
  <url-pattern>/myServlet</url-pattern>
</servlet-mapping>
▶ Comparison
Annotations (@WebServlet)
No XML needed
Compact, readable
Requires Servlet 3.0+
Harder to change without recompile
web.xml
External configuration
Change without recompile
Works with all versions
Verbose for many servlets
Modern projects: annotations preferred
View Layer

JSP

A JSP is translated into a servlet that writes HTML.
Scripting Elements — Scriptlet <% %>, Declaration <%! %>, Expression <%= %> for embedding Java in HTML. W3Schools →
Scripting Elements
<!-- Scriptlet: Java code in service method -->
<%
  String name = "User";
  out.println("Hello " + name);
%>

<!-- Declaration: Class-level variable/method -->
<%!
  int count = 0;
  public int getCount() {
    return ++count;
  }
%!>

<!-- Expression: Print value directly -->
Current Count: <%= getCount() %>

<!-- No semicolon in expression! -->
<%= "Hello World" %>
▶ Element Types
Scriptlet <% %>
Java code inside service method
Scope: request processing only
Can use out, request, response
Declaration <%! %>
Variables/methods at class level
Scope: entire servlet instance
Shared across all requests
Expression <%= %>
Equivalent to out.println()
No semicolon needed
Evaluates and outputs result
Directives — @page, @include, @taglib control translation-time behavior and imports.
Directives
<%@ page %> — Page attributes -->
<%@ page
  language="java"
  contentType="text/html; charset=UTF-8"
  import="java.util.*, java.sql.*"
  errorPage="error.jsp"
  session="true" %>

<%@ include %> — Static include -->
<%@ include file="header.jsp" %>

<%@ taglib %> — Custom tag libraries -->
<%@ taglib
  uri="http://java.sun.com/jsp/jstl/core"
  prefix="c" %>
▶ Directive Summary
@page
language, contentType, import
errorPage, session, buffer
Controls page-level settings
@include
Static file inclusion at translation
Included content merged into JSP
One copy, shared headers/footers
@taglib
Import custom tag libraries
Prefix maps to URI of TLD
Enables <c:if>, <c:forEach>
Best Practice: Avoid heavy scriptlets — use JavaBeans or MVC
JSP Lifecycle — JSP is translated to a Servlet, compiled, and executed. Cached until the JSP file changes.
Lifecycle Steps
// JSP Lifecycle (automatic by JSP engine)

1. JSP Engine loads index.jsp

2. Translation — converts to index_jsp.java
   // HTML becomes println() statements
   // JSP tags become Java code
   // Directives configure the servlet

3. Compilation — javac to index_jsp.class

4. Execution — service() generates HTML

5. Response — HTML sent to browser

// Key insight:
// JSP IS a Servlet under the hood
// The engine caches the compiled version
// Only recompiles when JSP changes
▶ Use Cases
When to Use JSP
Dynamic content (user-specific data)
Database integration via JDBC
Enterprise applications with Servlets
MVC Pattern
Servlet = Controller (logic)
JSP = View (presentation)
JavaBean = Model (data)
JSP vs Servlet
JSP — HTML-centric with Java snippets
Servlet — Java-centric with HTML output

Struts 1

The ActionServlet reads the config and routes to a JSP.
Struts 1 Flow — Request → ActionServlet → struts-config.xml → JSP. Uses MVC pattern with XML-based configuration. W3Schools →
Request Flow
// Struts 1 MVC Request Flow

1. Client sends: /hello.do

2. ActionServlet (Front Controller)
   ↓ parses URL, reads struts-config.xml

3. struts-config.xml (Action Mapping)
   <action path="/hello"
             forward="/pages/Hello.jsp"/>

4. Forward to Hello.jsp

5. JSP reads MessageResources.properties
   <bean:message key="hello.message"/>

6. Response: "Hello World"
▶ Flow Diagram
MVC Components
Model — JavaBeans, EJBs
View — JSP pages
Controller — ActionServlet
Request Lifecycle
Client → ActionServlet
ActionServlet → struts-config.xml
struts-config.xml → Action class
Action class → JSP
JSP → Response to client
struts-config.xml — maps URL patterns to JSP pages and defines message resources for i18n.
struts-config.xml
<struts-config>

  <action-mappings>
    <action
      path="/hello"
      forward="/pages/Hello.jsp"/>
  </action-mappings>

  <message-resources
    parameter="MessageResources"/>

</struts-config>

<!-- Key attributes -->
// path     = URL pattern (appended with .do)
// forward  = destination JSP
// name     = form bean name (optional)
// type     = Action class (optional)
▶ Action Mapping
URL Pattern
/hello maps to /hello.do
ActionServlet strips .do
Looks up /hello in config
Common Attributes
path — URL to match
forward — JSP destination
name — form bean reference
type — Action class name
scope — request or session
Multiple mappings allowed
MessageResources — i18n text stored in .properties files. Referenced via <bean:message> tag in JSP.

XML & DTD

A DTD checks the document's structure is valid.
XML Rules — well-formed XML requires one root element, case sensitivity, proper closing tags, and quoted attributes. W3Schools →
XML Rules
<!-- Rule 1: One root element required -->
<root>
  <child>content</child>
</root>

<!-- Rule 2: Case sensitive -->
<Tag>content</Tag>     ← OK
<tag>content</tag>     ← different element!

<!-- Rule 3: Every tag needs a closing tag -->
<tag></tag>              ← full form
<tag/>                   ← self-closing

<!-- Rule 4: Attribute values in quotes -->
<tag attr="value"/>
<tag attr='value'/>
▶ Purpose
What is XML?
eXtensible Markup Language
Self-describing data format
Platform & language independent
Common Uses
Data transfer between systems
Configuration files
Custom markup for structured data
Java Web XML Files
web.xml — Servlet config (DTD)
struts-config.xml — Struts config
pom.xml — Maven config (Schema)
DTD (Document Type Definition) — defines the structure and allowed elements/attributes of an XML document. W3Schools →
DTD Syntax
<!-- Reference DTD in XML -->
<?xml version="1.0"?>
<!DOCTYPE teams SYSTEM "teams.dtd">

<!-- Element declarations -->
<!ELEMENT teams (team+)>
<!ELEMENT team (name, salary)>
<!ELEMENT name (#PCDATA)>
<!ELEMENT salary (#PCDATA)>

<!-- Attribute declaration -->
<!ATTLIST team
  aid ID #REQUIRED>

<!-- ATTLIST format: -->
<!ATTLIST element-name
  attr-name attr-type default>
▶ DTD Symbols
Occurrence Symbols
+ — 1 or more
* — 0 or more
? — 0 or 1 (optional)
Combination Symbols
| — OR (A|B|C)
(,) — AND (comma-separated)
Data Types
#PCDATA — parsed text content
EMPTY — no content
ANY — any content allowed
Attribute Defaults
#REQUIRED — mandatory
#IMPLIED — optional
#FIXED "val" — fixed value
Complete DTD Example — a teams DTD defining structure, data types, and a required unique ID attribute.
teams.dtd
<!-- teams.dtd -->
<!ELEMENT teams (team+)>
<!ELEMENT team (name, salary)>
<!ELEMENT name (#PCDATA)>
<!ELEMENT salary (#PCDATA)>
<!ATTLIST team aid ID #REQUIRED>

<!-- teams.xml -->
<?xml version="1.0"?>
<!DOCTYPE teams SYSTEM "teams.dtd">
<teams>
  <team aid="t1">
    <name>Arun</name>
    <salary>50000</salary>
  </team>
  <team aid="t2">
    <name>Priya</name>
    <salary>62000</salary>
  </team>
</teams>
▶ Validation
DTD Validates
Element structure (nesting)
Order of child elements
Number of occurrences (+, *, ?)
Required attributes
This DTD says
teams contains 1+ team
team has name then salary
team requires aid attribute
aid must be unique ID type
DTD checks structure only, not data types
Validation

XSD Schema

A schema (XSD) also checks the data type — e.g. integer.
XML Schema (XSD) — more powerful than DTD. Supports data types, namespaces, inheritance, and content + structure validation. W3Schools →
Schema Basic Structure
<xs:schema
  xmlns:xs="http://www.w3.org/2001/XMLSchema">

  <!-- Complex Type -->
  <xs:complexType name="teamType">
    <xs:sequence>
      <xs:element name="name"
                  type="xs:string"/>
      <xs:element name="salary"
                  type="xs:integer"/>
    </xs:sequence>
    <xs:attribute name="aid"
                  type="xs:ID"
                  use="required"/>
  </xs:complexType>

  <!-- Root Element -->
  <xs:element name="teams">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="team"
                    type="teamType"
                    maxOccurs="unbounded"/>
      </xs:sequence>
    </xs:complexType>
  </xs:element>

</xs:schema>
▶ Simple vs Complex
Simple Types
Text, numbers, dates
xs:string, xs:integer
xs:date, xs:boolean
No children or attributes
Complex Types
Elements with children
Elements with attributes
Can combine simple + complex
Occurrence Attributes
minOccurs — minimum count
maxOccurs — "unbounded" = unlimited
xs:sequence and xs:attribute — sequence enforces element order, attributes define metadata on elements.
Schema Details
<!-- xs:sequence — ordered children -->
<xs:complexType>
  <xs:sequence>
    <xs:element name="first"
                type="xs:string"/>
    <xs:element name="last"
                type="xs:string"/>
  </xs:sequence>
</xs:complexType>

<!-- xs:attribute — element metadata -->
<xs:attribute name="id"
              type="xs:integer"
              use="required"/>

<xs:attribute name="lang"
              type="xs:string"
              use="optional"
              default="en"/>

<!-- use values -->
required  = mandatory attribute
optional  = can be omitted
prohibited = must not be present
▶ Common Patterns
xs:sequence
Children must appear in order
All children required by default
Use minOccurs/maxOccurs to adjust
xs:choice
Only one child allowed
Like DTD's pipe (|) operator
xs:all
Children in any order
Each child 0 or 1 times
xs:any
Allows any element
Like DTD's ANY keyword
DTD vs Schema — Schema is XML-based with rich data types and namespace support. DTD is simpler but limited.
