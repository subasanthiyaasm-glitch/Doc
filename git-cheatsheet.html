Key Concepts

Core terms every Git user should know before writing their first command. Git Book →
📦 Repository (Repo)

A project folder that Git tracks. Contains all your files plus the complete history of every change ever made, stored in a hidden .git folder.

git init git clone <url>
🌿 Branch

An independent line of work — like a parallel universe for your code. main is the default branch. Create a branch to work on a feature without touching main code.

git switch -c feature/x
📸 Commit

A saved snapshot of your staged files. Each commit has a unique ID (hash), an author, a timestamp, and your message. Think of it as a checkpoint you can always return to.

git commit -m "message"
🔀 Pull Request / MR

A request to merge your branch into another (usually main). GitHub calls it a Pull Request (PR); GitLab calls it a Merge Request (MR). Used for code review before merging.

via GitHub / GitLab UI
☁️ Remote

A copy of your repo hosted on a server (GitHub, GitLab, Bitbucket). The default remote is named origin. You push to share and pull to sync.

git remote add origin <url>
🍴 Fork vs Clone

Fork = your personal copy of someone else's repo on GitHub (server-side). Clone = download any repo to your machine (local copy). Fork first, then clone your fork.

git clone <your-fork-url>

Setup

💡 Run these once after installing Git. Your name and email tag every commit you make.
Set your identity and preferred editor globally. git-config docs →
~/.gitconfig
# Set identity
git config --global user.name  "Your Name"
git config --global user.email "you@email.com"

# Default branch name
git config --global init.defaultBranch main

# Preferred editor
git config --global core.editor "code --wait"

# View all settings
git config --list
▶ Scopes

--global → ~/.gitconfig
  applies to all your repos

--local → .git/config
  applies to this repo only

--system → system-wide
  applies to all users on the machine

Stage & Commit

The core git loop: edit → add → commit. Repeat forever. git-add docs →
stage & commit
# Stage a specific file
git add index.html

# Stage everything changed
git add .

# Stage parts of a file (interactive)
git add -p

# Commit staged changes
git commit -m "your message"

# Stage all tracked files + commit
git commit -am "quick commit"

# See working tree status
git status

# Compact status
git status -s
▶ Status symbols

M — modified, not staged

M — modified & staged

A — new file, staged

D — deleted

? — untracked


Good commit messages:
feat: add dark mode
fix: login crash on iOS
docs: update README

View history with git log — compact one-line view is the most useful day-to-day. git-log docs →
history
# Full commit history
git log

# Compact one line per commit
git log --oneline

# Visual branch graph
git log --oneline --graph --all

# What changed in a file
git diff index.html

# What's staged (not yet committed)
git diff --staged
▶ Example
* a3f1c2d fix login bug
* 9d2b4e1 add dark mode
* c7a0f53 initial commit

Push & Pull (Remote)

Connect to GitHub and sync changes. The remote is usually named origin. git-remote docs →
remote
# Clone a repo from GitHub
git clone https://github.com/user/repo.git

# Add a remote (after git init)
git remote add origin https://github.com/you/repo.git

# Push and set upstream tracking
git push -u origin main

# Push current branch
git push

# Pull latest changes (fetch + merge)
git pull

# Fetch without merging
git fetch

# List all remotes
git remote -v
▶ First push

1. Create repo on github.com

2. git remote add origin <url>

3. git push -u origin main


After that, just git push.


fetch = download only
pull = fetch + merge
clone = first-time download

Pull Request (PR) & Merge Request (MR)

🔀 GitHub calls it a Pull Request (PR). GitLab calls it a Merge Request (MR). Same concept — you're asking to merge your branch into another, usually after code review.
Typical PR/MR workflow — feature branch to main. GitHub Docs →
pr / mr workflow
# 1. Create a feature branch
git switch -c feature/login

# 2. Make your changes, then stage & commit
git add .
git commit -m "feat: add login page"

# 3. Push the branch to GitHub/GitLab
git push -u origin feature/login

# 4. Open a PR/MR on GitHub/GitLab UI
#    → Compare feature/login with main
#    → Add title, description, reviewers

# 5. After approval, merge on the UI
#    (or via CLI with gh tool)
gh pr create --title "Add login page" --base main

# 6. Clean up your local branch
git switch main
git pull
git branch -d feature/login
▶ PR tips

Good PR description:

• What does it do?

• Why was it needed?

• How to test it?


PR vs Direct push:
Small solo project → push
Team / open source → PR/MR


Draft PR: open early
to share progress without
requesting a full review yet.

Sync your feature branch with the latest main before opening a PR to avoid conflicts. git-rebase docs →
sync before PR
# Make sure main is up to date
git switch main
git pull

# Go back to your branch
git switch feature/login

# Option A: merge main into your branch
git merge main

# Option B: rebase on top of main (cleaner history)
git rebase main

# Push updated branch (rebase needs force push)
git push --force-with-lease
▶ Merge vs Rebase

Merge
Creates a merge commit.
History shows parallel work.
Safer, non-destructive.


Rebase
Re-applies your commits on top.
History stays linear, cleaner.
Rewrites commits — don't use
on shared/public branches.

Undo Things

⚠️ Never use git reset --hard or git push --force on shared branches — it rewrites history for everyone. Use git revert on shared branches instead.
Safe and unsafe ways to undo — choose based on whether the commit is already pushed. git-reset docs →
undo
# Discard changes in working dir
git restore index.html

# Unstage a file (keep changes)
git restore --staged index.html

# Amend last commit message
git commit --amend -m "corrected message"

# Undo last commit → keep staged
git reset --soft HEAD~1

# Undo last commit → keep unstaged
git reset HEAD~1

# Undo last commit → discard changes!
git reset --hard HEAD~1

# Safe undo: new "revert" commit
git revert HEAD

# Inspect a past commit (read-only)
git checkout a3f1c2d
▶ Which one?

restore
 unsaved edits in working dir

restore --staged
 undo git add

reset --soft
 undo commit, keep staged

reset
 undo commit, keep unstaged

reset --hard
 undo commit, lose changes

revert
 safe for pushed commits


When in doubt → revert

Inspect & Search

Find what changed, who changed it, and when — all without breaking anything. git-log docs →
inspect
# Show details of a specific commit
git show a3f1c2d

# Who changed each line of a file
git blame index.html

# Search commits by message
git log --grep="login"

# Find commits that changed a string
git log -S "myFunction"

# Compare two branches
git diff main..feature/login

# Files changed in last commit
git show --stat HEAD

# Binary search for a bad commit
git bisect start
git bisect bad           # current is broken
git bisect good a3f1c2d  # this commit was fine
▶ HEAD tips

HEAD = current commit

HEAD~1 = 1 commit back

HEAD~3 = 3 commits back

HEAD^ = same as HEAD~1


Best history view:
git log --all --oneline --graph

Stash

Temporarily shelve work so you can switch context without committing unfinished changes. git-stash docs →
stash
# Save current changes
git stash

# Stash with a description
git stash push -m "WIP: dark mode"

# List all stashes
git stash list

# Apply latest stash (keep it)
git stash apply

# Apply and remove latest stash
git stash pop

# Apply a specific stash
git stash apply stash@{2}

# Delete a stash
git stash drop stash@{0}

# Delete all stashes
git stash clear
▶ Common scenario

1. Working on a feature

2. Urgent bug comes in

3. git stash

4. git switch main

5. Fix the bug, commit it

6. git switch feature/x

7. git stash pop

8. Continue where you left off 🎉
