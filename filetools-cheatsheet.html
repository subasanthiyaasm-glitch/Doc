How It Works

A file is just a box of saved data. Almost everything you do with files is one of a few simple moves. Watch each card below to see the idea in motion — one calm step at a time.

Create

Make a brand-new file and start writing content into it.

Read

Open a file and look at what is stored inside, without changing it.

Update

Edit a file that already exists — change or add to its content.

Delete

Remove a file you no longer need, sending it to the trash.

Move / Copy

Send a file to another folder, or duplicate it somewhere new.

Zip / Compress

Squeeze one or more files into a smaller archive to save space.

Checksum

A checksum is a fixed-size value computed from data to detect errors; a rolling checksum can be updated incrementally as a window slides, while a strong checksum (hash) provides full collision-resistant verification. W3Schools →
Rolling vs Strong Checksum
// Rolling Checksum — fast, incremental
// Used to find matching blocks efficiently
// Example: Adler-32 / Rabin fingerprint
// Slides a window across the data;
// new value = old − outgoing + incoming

// Strong Checksum — slow, collision-resistant
// Used to verify final data integrity
// Example: SHA-256, MD5
// Must recompute over entire data
Rolling Checksum
O(1) per step — just adjust window
Detects block boundaries cheaply
Weak — not suitable for integrity alone

Strong Checksum
O(n) — full pass over data
Cryptographically secure (SHA-256)
Used for download verification
Checksums are essential for integrity verification (detecting corruption in transit) and deduplication (identifying identical files by their hash). W3Schools →
Use Cases
// Integrity Verification
// Compare checksum before and after transfer
// if (md5(file1) == md5(file2)) → OK

// Deduplication
// Store only unique content-addressed blocks
// Git objects are SHA-1 keyed by content
// Backup tools skip files with matching hash

// Java: Compute MD5 Checksum
import java.security.MessageDigest;
import java.io.FileInputStream;

public class ChecksumUtil {
  public static byte[] md5(String path)
      throws Exception {
    MessageDigest md =
        MessageDigest.getInstance("MD5");
    FileInputStream fis =
        new FileInputStream(path);
    byte[] buf = new byte[8192];
    int n;
    while ((n = fis.read(buf)) != -1) {
      md.update(buf, 0, n);
    }
    fis.close();
    return md.digest();
  }

  public static String toHex(byte[] bytes) {
    StringBuilder sb = new StringBuilder();
    for (byte b : bytes)
      sb.append(String.format("%02x", b));
    return sb.toString();
  }
}
Integrity Verification
download_file.zip → sha256: a3f2...
publisher sha256: a3f2... → match ✓

Deduplication
file_a.jpg → sha256: 7b1c...
file_b.jpg → sha256: 7b1c...
→ same content, store once

Hashing Algorithms

Common hash algorithms differ in output size, speed, and security — MD5 and SHA-1 are fast but vulnerable; SHA-256 and SHA-512 are secure for most use cases. W3Schools →
Algorithm Comparison
// MD5 — 128-bit (16 bytes)
// Speed: Fastest | Status: BROKEN
// Use: Non-crypto checksums only

// SHA-1 — 160-bit (20 bytes)
// Speed: Fast | Status: DEPRECATED
// Use: Legacy Git, TLS certs phasing out

// SHA-256 — 256-bit (32 bytes)
// Speed: Moderate | Status: SECURE
// Use: TLS, certificates, file verification

// SHA-512 — 512-bit (64 bytes)
// Speed: Slower on 32-bit CPUs | Status: SECURE
// Use: High-security applications
Algorithm Bits Hex Len Status
MD5 128 32 Broken
SHA-1 160 40 Deprecated
SHA-256 256 64 Secure
SHA-512 512 128 Secure
Java's MessageDigest class provides a provider-agnostic API for computing hashes; call getInstance("SHA-256") and feed data via update(). W3Schools →
Java MessageDigest
import java.security.MessageDigest;

public class HashDemo {
  public static void main(String[] args)
      throws Exception {
    String data = "Hello, World!";

    // MD5
    MessageDigest md5 =
        MessageDigest.getInstance("MD5");
    byte[] hash5 = md5.digest(
        data.getBytes());

    // SHA-256
    MessageDigest sha256 =
        MessageDigest.getInstance("SHA-256");
    byte[] hash256 = sha256.digest(
        data.getBytes());

    // SHA-512
    MessageDigest sha512 =
        MessageDigest.getInstance("SHA-512");
    byte[] hash512 = sha512.digest(
        data.getBytes());

    System.out.println(toHex(hash5));
    System.out.println(toHex(hash256));
    System.out.println(toHex(hash512));
  }

  static String toHex(byte[] bytes) {
    StringBuilder sb = new StringBuilder();
    for (byte b : bytes)
      sb.append(String.format("%02x", b));
    return sb.toString();
  }
}

Rsync

rsync synchronizes files between locations using delta-transfer — only changed blocks are sent, making it efficient for local and remote sync. W3Schools →
Basic Commands
$ rsync -avz src/ dest/          # local sync
$ rsync -avz src/ user@host:dest/ # push to remote
$ rsync -avz user@host:src/ dest/ # pull from remote
$ rsync -avzP large.bin host:/tmp/ # resume + progress
Local sync (note trailing slash):
rsync -avz src/ dest/
src/ → contents of src go into dest/
src → src directory itself goes into dest/

Remote sync:
rsync -avz src/ user@server:/data/
Uses SSH by default (port 22)
Key rsync options: -a archive mode, -v verbose, -z compress, --delete remove extraneous files, -P progress + partial. W3Schools →
Options Reference
$ rsync -a src/ dest/     # archive: perms, symlinks, etc.
$ rsync -v src/ dest/     # verbose output
$ rsync -z src/ dest/     # compress during transfer
$ rsync --delete src/ dest/ # delete files not in src
$ rsync -P src/ dest/     # --progress --partial
$ rsync -n src/ dest/     # dry run (preview only)
$ rsync --exclude "*.log" src/ dest/
$ rsync -e "ssh -p 2222" src/ host:dest/
$ rsync -avz --progress src/ dest/
-a expands to:
-rlptgoD
r=recursive l=links p=perms
t=times g=group o=owner D=devices

--delete behavior:
src has: a.txt b.txt
dest has: a.txt c.txt
→ dest becomes: a.txt b.txt
(c.txt removed!)

-n dry run shows what would change

Rsync Algorithm

The rsync algorithm uses a rolling checksum (Adler-32 variant) to find matching blocks between old and new files, then transfers only the deltas. W3Schools →
Rolling Checksum (Adler-32 Variant)
// Adler-32: two 16-bit accumulators
// A = (1 + each byte) mod 65521
// B = (all A values summed) mod 65521
// checksum = (B << 16) | A

// Rolling property:
// Remove leftmost byte, add rightmost byte
// O(1) update per window slide

// Used as a quick filter:
// if rolling checksum matches → verify with strong hash
// if rolling checksum differs → definitely no match
Window: [A B C D E] (size 5)
Rolling step → [B C D E F]

Adler-32 Formula:
A = (A − old_byte + new_byte) % 65521
B = (B − block_size×old_byte + A) % 65521

Cost: O(1) per byte moved
vs O(n) for full recomputation
The block-level sync workflow: sender splits old file into blocks, receiver computes rolling checksums and sends back matching block indices, then only non-matching blocks are transferred. W3Schools →
Block-Level Sync Workflow
// Step 1: Sender splits OLD file into blocks
//   Block 0: [A B C D] → strong: sha_0
//   Block 1: [E F G H] → strong: sha_1
//   Block 2: [I J K L] → strong: sha_2

// Step 2: Receiver slides window over NEW file
//   computes rolling checksum at each offset
//   sends (offset, rolling_checksum) to sender

// Step 3: Sender matches rolling → strong hash
//   sends back: list of (offset, block_index)
//   or "no match" for unmatched blocks

// Step 4: Receiver reconstructs:
//   matched blocks → copy from old file
//   unmatched blocks → literal data from new
Delta Transfer Workflow

OLD file (sender):
┌────────┬────────┬────────┐
│ Block0 │ Block1 │ Block2 │
│ ABCD │ EFGH │ IJKL │
└────────┴────────┴────────┘

NEW file (receiver):
┌────────┬────────┬────────┐
│ ABCD │ EFXX │ IJKL │
│ match✓ │ Δdata │ match✓ │
└────────┴────────┴────────┘

Transfer: only "XX" delta (Block 1)
Saves bandwidth vs sending full file

Shell Commands

Core file integrity and comparison commands: md5sum, sha256sum, rsync, diff, and cmp. W3Schools →
Checksum Commands
$ md5sum file.zip
3a7bd3e2360a3d29eea436fcfb7e44c7  file.zip

$ sha256sum file.zip
a3f2b8c1d4e5f6a7b8c9d0e1f2a3b4c5  file.zip

# Verify against known checksum
$ sha256sum -c checksums.txt
file.zip: OK
file.iso: FAILED

# Checksum of a string
$ echo -n "hello" | md5sum
5d41402abc4b2a76b9719d911017c592
md5sum output format:
<32-char hex> <filename>

sha256sum output format:
<64-char hex> <filename>

-c (check mode):
Reads checksums.txt file
OK → file matches
FAILED → file corrupted
FAILED open or read → missing

macOS: use shasum -a 256 instead
Sync directories with rsync, compare files with diff, and do byte-level comparison with cmp. W3Schools →
Sync & Compare Commands
# Rsync — incremental file sync
$ rsync -avz src/ dest/
$ rsync -avz --delete src/ dest/
$ rsync -avzP src/ host:backup/

# Diff — line-by-line comparison
$ diff file1.txt file2.txt
$ diff -u old.py new.py     # unified format
$ diff -r dir1/ dir2/       # recursive

# Cmp — byte-by-byte comparison
$ cmp file1.bin file2.bin
$ cmp -l file1.bin file2.bin # show all diffs
diff output (unified):
--- old.py
+++ new.py
@@ -1,3 +1,4 @@
-old line
+new line

cmp output:
files identical → no output (exit 0)
files differ → "differ at byte 42"

diff — text-level (line by line)
cmp — binary-level (byte by byte)
