Basic

Fundamentals — What is HLD?

High-Level Design defines the system architecture: components, their responsibilities, and how they interact — without implementation detail.
HLD vs LLD
─────────────────────────────────────────────
HLD (High-Level Design)
  • Architecture overview
  • Component identification (DB, Cache, Queue…)
  • Data flow between components
  • Tech stack choices  (SQL vs NoSQL, REST vs gRPC)
  • Scalability & reliability strategy
  • No code / pseudocode

LLD (Low-Level Design)
  • Class diagrams, method signatures
  • DB schema (exact tables & columns)
  • Algorithms & data structures
  • Edge-case handling in code

─────────────────────────────────────────────
Order:  Requirements → HLD → LLD → Code
Key Goals of HLD
  • Clarity — any engineer can understand the system without reading code
  • Scalability — handles 10× growth with config/infra changes only
  • Reliability — survives component failures gracefully
  • Maintainability — components can evolve independently
  • Latency — p99 SLAs are achievable with the chosen design
  • Cost — resource usage is proportional to load
Standard HLD Components
Client          # Browser / Mobile / CLI
  ↓
DNS             # Resolves domain → IP
  ↓
CDN             # Edge cache for static assets
  ↓
Load Balancer   # Distributes traffic (L4 / L7)
  ↓
API Gateway     # Auth, rate-limit, routing
  ↓
Services        # Business logic (monolith or µservice)
  ↓
Cache           # Redis / Memcached (fast reads)
Database        # Persistent storage (SQL / NoSQL)
Message Queue  # Async work (Kafka / RabbitMQ)
Object Store   # Files / media (S3)
Search Index   # Full-text (Elasticsearch)

Scalability

Scalability is the ability to handle increased load by adding resources without redesigning the system.
Vertical vs Horizontal Scaling
Vertical Scaling (Scale Up)
  Bigger machine: more CPU, RAM, SSD
  • Simple — no code change needed
  • Hard limit: largest available machine
  • Single point of failure
  • Example: RDS instance upgrade

Horizontal Scaling (Scale Out)
  More machines running same service
  • Handles unlimited load (theoretically)
  • Requires stateless services
  • Needs load balancer in front
  • Example: add EC2 instances behind ALB

──────────────────────────────────────────────
Rule of thumb:
  Start vertical → hit limits → go horizontal
Stateless vs Stateful
StatelessStateful
Session dataExternal store (Redis)In-process memory
Horizontal scaleEasyHard
Rolling deploySafeSticky sessions needed
ExampleREST API serverWebSocket game server
Key insight: Move state to the edges (DB, cache) so all app servers are identical and interchangeable.
Scalability Patterns
1. Replication
   Copy data to multiple nodes
   → Primary handles writes; replicas handle reads

2. Partitioning / Sharding
   Split data across nodes by key
   → shard_id = hash(user_id) % num_shards

3. Caching
   Store hot data in fast memory
   → Redis, Memcached in front of DB

4. Async Processing
   Offload heavy work to queues
   → Return 202 Accepted; process in background

5. CDN
   Serve static assets from edge nodes
   → Reduces origin load + latency

6. Microservices
   Scale each service independently
   → Checkout scales × 10 during flash sale
QPS Estimation
Twitter-scale example
300M DAU, 60% active daily
Avg 5 actions/day per user
QPS = (300M × 0.6 × 5) / 86400
    ≈ 10,400 QPS
Peak ≈ 3× avg = ~30K QPS
Storage example
100M tweets/day × 280 chars × 2B
= 56 GB/day
= ~20 TB/year

Load Balancing

A load balancer distributes incoming requests across multiple backend servers to maximize availability and throughput.
LB Algorithms
Round Robin
  req1→S1, req2→S2, req3→S3, req4→S1…
  • Simple, equal distribution
  • Bad if servers have unequal capacity

Weighted Round Robin
  S1 weight=3, S2 weight=1 → 75% to S1
  • Use when servers differ in spec

Least Connections
  Route to server with fewest active conns
  • Best for long-lived connections

IP Hash (Sticky sessions)
  hash(client_ip) % num_servers → always same
  • Needed for stateful services

Random
  Pick a random server
  • Simple; good under uniform load

Resource-Based
  Route based on server CPU/mem metrics
  • Most accurate; requires health agent
L4 vs L7 Load Balancer
L4 (Transport)L7 (Application)
Works atTCP/UDP layerHTTP layer
Routing byIP + portURL, headers, cookies
SpeedFasterSlightly slower
SSL terminationNoYes
Path routingNoYes
ExamplesAWS NLB, HAProxyAWS ALB, Nginx, Envoy
Health checks: LB pings /health every N seconds. Remove unhealthy nodes automatically → no manual intervention needed.
DNS Load Balancing
# DNS returns multiple A records
api.example.com → 1.2.3.4, 1.2.3.5, 1.2.3.6

# Client picks one (usually first)
# TTL controls how often client re-resolves

Geo DNS
  US users  → us-east servers
  EU users  → eu-west servers
  APAC users→ ap-south servers

# Reduces cross-region latency by 100-200ms
# Providers: Route53, Cloudflare, Akamai
LB Failure Modes
  • Active-Passive: standby LB takes over if primary fails (failover ~30s)
  • Active-Active: both LBs serve traffic, Anycast routes to nearest
  • Hot standby: secondary receives health checks but no real traffic
  • Connection draining: LB waits for in-flight requests before removing a node (deregistration delay)

Caching

Caching stores expensive computation or data in fast memory so subsequent requests are served in microseconds instead of milliseconds.
Cache Strategies
Cache-Aside (Lazy loading — most common)
  1. App checks cache → miss?
  2. App reads DB → writes to cache
  3. Next read hits cache

Write-Through
  App writes to cache AND DB atomically
  • Cache always consistent with DB
  • Write latency = DB latency (slower writes)

Write-Behind (Write-Back)
  App writes to cache; async flush to DB
  • Fast writes; risk of data loss on crash

Read-Through
  Cache sits in front; fills itself from DB
  • App never talks to DB directly
  • Good for read-heavy workloads

Refresh-Ahead
  Cache proactively refreshes before TTL
  • No cold-start; slightly stale data ok
Cache Eviction Policies
PolicyEvictsBest For
LRULeast Recently UsedGeneral workloads
LFULeast Frequently UsedSkewed access (hot keys)
FIFOOldest entryTime-ordered data
TTLExpired entriesTime-sensitive data
RandomRandom entrySimple; low overhead
Cache Problems & Fixes
Cache Stampede (Thundering Herd)
  Problem: TTL expires → 1000 reqs hit DB simultaneously
  Fix:
    • Mutex lock: first miss acquires lock, others wait
    • Probabilistic early refresh: refresh before TTL
    • Background refresh thread

Cache Penetration
  Problem: request for non-existent key bypasses cache
  Fix:
    • Cache NULL values with short TTL
    • Bloom filter: fast check "key exists in DB?"

Cache Avalanche
  Problem: many keys expire at same time → DB overload
  Fix:
    • Jitter: TTL = base + rand(0, base×0.2)
    • Stagger expiry times on bulk loads

Hot Key
  Problem: one cache key gets 80% of reads → bottleneck
  Fix:
    • Local in-process cache (L1 cache)
    • Shard hot key: key_1, key_2 … key_N
Where to Cache
L1: Client-side Browser cache, service worker — 0ms
L2: CDN Edge Cloudflare, Fastly — ~5ms (nearest PoP)
L3: API Gateway Response cache for identical requests
L4: App-level In-process cache (Guava, Caffeine) — ~0.1ms
L5: Distributed Redis cluster — ~0.5ms
L6: DB buffer Postgres shared_buffers, InnoDB pool
Hit rate goal: ≥ 90% at L5 to avoid DB bottleneck.

Databases

Database choice drives consistency, scalability, and query flexibility. Match the storage engine to the data model and access patterns.
SQL vs NoSQL
SQL (Relational — Postgres, MySQL)
  • ACID transactions (strong consistency)
  • Structured schema — enforced at DB level
  • Rich queries: JOINs, aggregations, subqueries
  • Vertical scaling primary; horizontal via read replicas
  • Use when: financial data, complex relationships,
             reporting, strong consistency required

NoSQL types:
  Document  → MongoDB, Firestore
    JSON documents; flexible schema; nested data
  Key-Value → Redis, DynamoDB
    Ultra-fast; simple get/set; no joins
  Wide-Col  → Cassandra, HBase
    Column families; massive write throughput
  Graph     → Neo4j, Amazon Neptune
    Nodes + edges; friend-of-friend queries
  Time-Series→ InfluxDB, TimescaleDB
    Optimized for timestamps + metrics
When to Use What
Use CaseChoice
User accounts, ordersPostgreSQL
Session / token storeRedis
Product catalogMongoDB
Activity feed / timelineCassandra
Social graphNeo4j
Full-text searchElasticsearch
Metrics / IoT dataInfluxDB
Files / blobsS3 / GCS
Analytics / OLAPSnowflake / BigQuery
Replication
Primary-Replica (Master-Slave)
  Primary: all writes
  Replicas: read-only copies (async replication)
  • Read scaling: distribute reads across replicas
  • Failover: promote replica if primary dies
  • Replication lag: replica may be slightly stale

Multi-Primary (Multi-Master)
  All nodes accept writes
  • Higher write availability
  • Conflict resolution required
  • Example: CockroachDB, Galera

Synchronous Replication
  Write ack only after replica confirms
  • Zero data loss; higher write latency

Asynchronous Replication
  Write ack immediately; replica updates eventually
  • Low latency; possible data loss on crash
Sharding (Partitioning)
Horizontal sharding — split rows across nodes
shard = hash(user_id) % 4
0 → Shard A   1 → Shard B
2 → Shard C   3 → Shard D
  • Range sharding: user_id 0–1M → Shard1; easy range queries
  • Hash sharding: uniform distribution; no range queries
  • Directory sharding: lookup table maps key → shard; flexible but single point
  • Geo sharding: US → Shard-US; EU → Shard-EU
  • Hotspot problem: celebrity user → one shard overloaded; add sub-sharding
ACID vs BASE
ACID (SQL databases)
  Atomicity    — all or nothing (no partial writes)
  Consistency  — DB always in valid state after txn
  Isolation    — concurrent txns don't interfere
  Durability   — committed data survives crashes

BASE (most NoSQL databases)
  Basically Available — responds even under failure
  Soft state          — state may change without input
  Eventually Consistent— all nodes converge over time

──────────────────────────────────────────────
ACID: Bank transfers, orders, inventory
BASE: Social feeds, view counts, likes
Indexing Essentials
Index TypeGood For
B-Tree (default)Range queries, ORDER BY, =, <, >
HashExact equality lookups only
CompositeMulti-column WHERE; column order matters
PartialIndex subset of rows (WHERE active=true)
CoveringAll query columns in index; no table scan
GIN / GiSTFull-text search, arrays, JSONB (Postgres)
Rule: Index columns in WHERE, JOIN, ORDER BY. Avoid over-indexing — each index slows writes.

CAP Theorem & PACELC

CAP states a distributed system can guarantee only 2 of 3 properties during a network partition. PACELC extends this to normal operation.
CAP Theorem
Consistency
  Every read returns the most recent write
  or an error. All nodes see same data.

Availability
  Every request gets a non-error response.
  (Not guaranteed to be the latest data)

Partition Tolerance
  System continues to function even when
  network messages are dropped/delayed.

─────────────────────────────────────────────
In practice: P is mandatory (networks fail).
So the real trade-off is C vs A.

CP: Consistent but may reject requests
    → HBase, ZooKeeper, Etcd, MongoDB

AP: Available but may return stale data
    → Cassandra, CouchDB, DynamoDB

CA: Only works if no network partition
    → Single-node RDBMS (not distributed)
PACELC Model
Extends CAP to cover normal operation (no partition)
If Partition: choose Availability or Consistency
Else: choose Latency or Consistency
SystemPartitionElse
DynamoDBPAEL (low latency)
CassandraPAEL
MongoDBPCEC
HBasePCEC
CockroachDBPCEC
Consistency Models (strongest → weakest)
Linearizability (Strict)
  Reads always see latest write. Like single machine.
  Cost: high latency, hard to scale.

Sequential Consistency
  All operations appear in some total order.
  Not necessarily real-time.

Causal Consistency
  Causally related operations seen in order.
  "Alice posts, then Bob replies" always ordered.

Read-Your-Writes
  You always read what you just wrote.
  Others may be stale. (most apps need this)

Monotonic Reads
  Once you read X, you never read older than X.

Eventual Consistency (weakest)
  If writes stop, all replicas will agree.
  No guarantee on WHEN.
  Example: DNS, social media likes
Choosing Consistency Level
  • Bank balance / inventory: Linearizability — must be exact
  • User profile updates: Read-your-writes — you see your own change
  • Social feed: Eventual — 200ms stale is fine
  • Like counts: Eventual — approximate is acceptable
  • Chat messages: Causal — replies must follow posts
  • Distributed locks: Linearizability — correctness critical

API Design

The API is the contract between clients and your system. Choose the protocol and style based on latency, coupling, and client diversity needs.
REST vs GraphQL vs gRPC
REST
  GET  /users/123          → get user
  POST /users              → create user
  PUT  /users/123          → replace user
  PATCH /users/123         → partial update
  DELETE /users/123        → delete user

  • Cacheable (HTTP cache headers)
  • Stateless; easy to reason about
  • Over/under-fetching common

GraphQL
  POST /graphql
  { user(id:"123") { name, email, posts { title } } }

  • Client specifies exact fields needed
  • Single endpoint; reduces round-trips
  • Harder to cache; N+1 query risk

gRPC
  rpc GetUser (UserRequest) returns (User) {}

  • Binary (Protobuf) — 5-10× smaller than JSON
  • Bi-directional streaming
  • Strong typing via .proto contract
  • Best for internal service-to-service
API Comparison
RESTGraphQLgRPC
TransportHTTP/1.1HTTP/1.1HTTP/2
PayloadJSONJSONProtobuf
CachingEasyHardManual
StreamingNoSubsYes
BrowserYesYesLimited
Best forPublic APIsMobile/BFFMicroservices
BFF pattern: Backend-for-Frontend — dedicated API layer per client type (iOS, web, Android) that aggregates microservice calls.
Rate Limiting Algorithms
Token Bucket
  Bucket holds N tokens; refills at R/sec
  Each request consumes 1 token
  Allow bursts up to bucket size
  → Most common; flexible burst handling

Leaky Bucket
  Requests enter queue; process at fixed rate
  Queue full → drop request
  → Smooth output; no burst allowed

Fixed Window Counter
  Count reqs in 1-minute window; reset at :00
  Risk: 2× limit possible at window boundary

Sliding Window Log
  Store timestamp of each request
  Count reqs in last 60s on each request
  → Accurate but memory-heavy

Sliding Window Counter
  Hybrid: current + prev window weighted
  → Good accuracy + low memory
API Gateway Responsibilities
  • Authentication: validate JWT / API key before forwarding
  • Rate limiting: per-user or per-IP request throttling
  • SSL termination: decrypt TLS; forward plain HTTP internally
  • Request routing: /users → user-service; /orders → order-service
  • Request transformation: add headers, rename fields
  • Response caching: cache identical GET responses at edge
  • Observability: log, trace, and metric every request
Examples: Kong, AWS API Gateway, Nginx, Traefik, Envoy

Message Queues & Event Streaming

Queues decouple producers from consumers, enabling async processing, load smoothing, and fault tolerance across services.
Queue vs Stream
Message Queue (RabbitMQ, SQS, ActiveMQ)
  • Message consumed ONCE by ONE consumer
  • Message deleted after processing
  • Work distribution: job queue, task runner
  • Use: email sending, image resize, payments

Event Stream (Kafka, Kinesis)
  • Message retained on disk (days/forever)
  • Multiple consumer groups read independently
  • Replay: reprocess historical events
  • Use: analytics, audit log, event sourcing,
         real-time pipelines, CDC

─────────────────────────────────────────────
Queue:  "do this task once"
Stream: "this event happened — anyone interested?"
Kafka Architecture
Core concepts
  • Topic: named log of events (like a DB table)
  • Partition: ordered sub-log; unit of parallelism
  • Offset: position of a message in a partition
  • Producer: writes events to a topic
  • Consumer Group: set of consumers sharing work; each partition → one consumer per group
  • Broker: Kafka server; stores partitions
  • Retention: configurable (7 days default); not tied to consumption
Throughput: 10M+ msgs/sec; p99 <10ms
Delivery Guarantees
At-most-once
  Send and forget. Never retry.
  → May lose messages; lowest overhead

At-least-once
  Retry until acked. May duplicate.
  → Default for most queues
  → Consumer must be idempotent

Exactly-once
  Producer dedup + transactional commits
  → Hardest; Kafka transactions support this
  → Use for financial, inventory updates

─────────────────────────────────────────────
Idempotency key pattern:
  PUT /payments/{idempotency_key}
  Same key → same result; no double charge
Common Queue Use Cases
PatternExample

Microservices

Microservices decompose a system into small, independently deployable services, each owning its data and business capability.
Monolith vs Microservices
Monolith
  Single deployable unit; shared DB
  ✓ Simple dev, test, deploy
  ✓ No network hops between modules
  ✗ Scales as a unit (can't scale just checkout)
  ✗ Tech stack locked in
  ✗ Large teams clash in same codebase

Microservices
  Services: User, Order, Payment, Notification…
  Each owns its own DB (polyglot persistence)
  Communicate via REST / gRPC / events
  ✓ Independent scale, deploy, tech stack
  ✓ Team autonomy (Conway's Law)
  ✗ Distributed system complexity
  ✗ Network latency on every call
  ✗ Distributed transactions are hard

Rule: Start monolith, extract services at seams
      when a team or scaling boundary is clear.
Service Communication
Synchronous (request-response)
  • REST / gRPC — caller blocks for result
  • Simple; tight coupling; cascade failures
  • Add circuit breaker + timeout
Asynchronous (event-driven)
  • Publish event; consumer processes later
  • Loose coupling; harder to trace
  • Use for: notifications, analytics, side effects
Service Discovery
  • Client-side: client queries registry (Eureka)
  • Server-side: LB queries registry (Consul + Nginx)
Circuit Breaker Pattern
States:
  CLOSED  → Normal operation; calls pass through
            Failure count tracked
  OPEN    → Too many failures; reject immediately
            Return fallback / error fast
            Wait cooldown period (e.g. 30s)
  HALF-OPEN→ Let one trial request through
            Success → CLOSED
            Failure → OPEN again

─────────────────────────────────────────────
Why: Prevents cascade failure.
If Payment Service is down, don't let
10K requests pile up waiting → CPU/thread
exhaustion takes down Order Service too.

Libraries: Hystrix (Netflix), Resilience4j,
            Polly (.NET), Tokio (Rust)
Resilience Patterns
  • Retry with backoff: retry after 1s, 2s, 4s… (exponential + jitter)
  • Timeout: never wait forever; set deadline on every call
  • Bulkhead: separate thread pools per dependency so one slow service can't exhaust all threads
  • Fallback: return cached result / default on failure
  • Idempotency: safe to retry; same result on repeated calls
  • Health check: /health and /ready endpoints for LB + orchestrator
  • Graceful degradation: recommendations fail → show popular items instead

Advanced Design Patterns

Architectural patterns for complex, large-scale systems. Each solves a specific class of problem — pick based on your constraints, not trends.
CQRS — Command Query Responsibility Segregation
# Separate read and write models

Write Side (Commands)
  POST /orders { items, payment }
  → Validate → apply business rules → save event
  → Optimized for correctness

Read Side (Queries)
  GET /orders/dashboard
  → Pre-built denormalized view (Redis / ES)
  → Optimized for speed

─────────────────────────────────────────────
Write DB: PostgreSQL (normalized, ACID)
Read DB:  Elasticsearch (flat, fast queries)
Sync:     Event stream (Kafka) rebuilds read views

Why:
  - Read traffic is 100× write traffic → scale separately
  - Complex read queries are slow on normalized write model
  - Enables multiple read projections for different clients
Event Sourcing
Store events, not current state
[AccountOpened, $0]
[Deposited, $500]
[Withdrawn, $200]
[Deposited, $100]
→ Replay → Balance: $400
  • Audit log free: every change is recorded
  • Time travel: rebuild state at any point in time
  • Event replay: rebuild projections after bugs
  • Snapshots: periodic state snapshot to avoid replaying all events
  • Complexity: harder to query current state; use projections
Saga Pattern — Distributed Transactions
# Problem: No 2PC across microservices
# Solution: sequence of local txns + compensations

Order Saga (Choreography)
  OrderService  → OrderCreated event
  PaymentService→ PaymentProcessed event
  InventoryService→ StockReserved event
  ShippingService → ShipmentCreated event

  On failure:
  PaymentFailed → CancelOrder (compensation)

Orchestration Saga
  SagaOrchestrator calls each service
  Knows the full flow; handles failures
  → Easier to monitor; single point of control

─────────────────────────────────────────────
vs 2PC (Two-Phase Commit):
  2PC: distributed lock → blocks; doesn't scale
  Saga: eventual consistency; compensations handle rollback
Other Advanced Patterns
  • Outbox Pattern: write event to DB in same transaction as data; relay process publishes to queue — ensures exactly-once delivery
  • Strangler Fig: gradually replace monolith by routing features to new microservices; old code shrinks over time
  • Sidecar: attach proxy container (Envoy) to each service pod for observability, mTLS, retries — no app code change
  • Anti-Corruption Layer: translate between legacy and new domain model so legacy doesn't pollute new design
  • Backends for Frontends: per-client API gateway aggregates services for mobile, web, TV separately

Reliability & Availability

Reliability engineering ensures systems meet SLAs under failure conditions through redundancy, observability, and operational discipline.
Availability Nines
SLA       Downtime/year  Downtime/month
99%       3.65 days       7.3 hours
99.9%     8.7 hours       43.8 minutes
99.99%    52 minutes      4.4 minutes
99.999%   5.3 minutes     26 seconds

─────────────────────────────────────────────
Composite availability:
  Two services each at 99.9% in series:
  0.999 × 0.999 = 99.8%  ← worse!

  Two services each at 99% in parallel (either works):
  1 - (0.01 × 0.01) = 99.99%  ← much better

Redundancy improves availability.
Dependencies degrade availability.
SLI / SLO / SLA
SLI — Service Level Indicator
Measured metric: request latency, error rate, availability
SLO — Service Level Objective
Target: p99 latency < 200ms; error rate < 0.1%
SLA — Service Level Agreement
Legal contract with customer: 99.9% uptime or refund
Error Budget
SLO=99.9% → 43min/month allowed downtime. Burn too fast → freeze deployments.
Disaster Recovery
RPO (Recovery Point Objective)
  Max acceptable data loss
  RPO = 1hr → restore from 1hr-old backup at worst

RTO (Recovery Time Objective)
  Max acceptable downtime
  RTO = 30min → system back up within 30 minutes

DR Strategies (cheapest → costliest)
  Backup & Restore
    Restore from S3 snapshots. Hours of RTO.
  Pilot Light
    Core systems run minimal in DR region.
    Scale up on disaster. 10-30 min RTO.
  Warm Standby
    DR runs at reduced capacity, ready to scale.
    Minutes of RTO.
  Active-Active Multi-Region
    All regions serve traffic simultaneously.
    Near-zero RTO & RPO. Most expensive.
Observability — 3 Pillars
  • Metrics: numeric measurements over time (QPS, latency, error rate, CPU) — Prometheus + Grafana. Alert on these.
  • Logs: structured timestamped event records (JSON). Centralize with ELK / Loki. Search when debugging.
  • Traces: end-to-end request path across services. Spans show time in each service. Use Jaeger / Zipkin / Tempo.
Golden signals (Google SRE): Latency, Traffic, Errors, Saturation (L-T-E-S). Monitor these for every service.
Intermediate

Security in System Design

Security must be designed in, not bolted on. Address authentication, authorization, encryption, and input validation at the architecture level.
Auth Patterns
Session-based Auth
  Login → server creates session in DB/Redis
  Cookie stores session_id
  Server validates session on each request
  • Stateful: easy revoke; hard to scale

JWT (JSON Web Token)
  Login → server signs token (secret/RSA key)
  Client sends Bearer token in header
  Server validates signature — no DB lookup
  • Stateless; fast; hard to revoke before expiry
  • Short TTL (15min) + refresh token pattern

OAuth 2.0 + OIDC
  Delegate auth to identity provider
  (Google, GitHub, Okta)
  Access token for APIs; ID token for identity
  • Best for third-party integrations & SSO

API Key
  Static key in header (X-API-Key)
  Good for server-to-server; easy to rotate
  • Must be stored hashed on server side
Security Layers
  • TLS everywhere: HTTPS externally; mTLS between internal services
  • Encrypt at rest: DB encryption, S3 SSE — protects stolen disks
  • Input validation: validate/sanitize at every boundary; never trust client input
  • Principle of least privilege: services only have access they need; scoped IAM roles
  • Secrets management: Vault, AWS Secrets Manager — never hardcode in code or env files
  • DDoS protection: rate limiting, Cloudflare WAF, auto-scaling capacity
  • Audit logging: who did what, when, from where — immutable append-only log

Back-of-Envelope Estimation

Quick estimation validates whether a design can meet scale requirements before committing to an architecture.
Power of 2 & Latency Numbers
Data sizes
  1 KB  = 10³ bytes     1 MB  = 10⁶ bytes
  1 GB  = 10⁹ bytes     1 TB  = 10¹² bytes

Latency numbers (2024 reference)
  L1 cache ref        0.5  ns
  L2 cache ref        7    ns
  RAM access          100  ns    ← ~100ns
  SSD random read     150  µs    ← ~0.15ms
  HDD random read     10   ms
  Network: same DC    0.5  ms
  Network: cross DC   30   ms
  Network: cross cont 150  ms

Throughput reference
  Gigabit network     100 MB/s
  SSD sequential      500 MB/s
  RAM read            10  GB/s

Time constants
  1 day  = 86,400 s   ≈ 10⁵ s
  1 year ≈ 3 × 10⁷ s
Estimation Template
Step 1 — Assumptions
State your numbers clearly: DAU, actions/user/day
Step 2 — QPS
QPS = (DAU × actions) / 86400
Peak QPS ≈ 2–3× avg QPS
Step 3 — Storage
daily = records/day × record_size

System Design Interview Blueprint

A repeatable framework for any system design interview. Spend time proportionally: requirements and estimation upfront, core design in the middle, deep-dives at the end.
45-Minute Framework
──────────────────────────────────────────────
[0-5 min]  Clarify Requirements
  • Functional: what does it do?
  • Non-functional: scale, latency, availability
  • Out of scope: what are you NOT building?
  • Ask: read-heavy or write-heavy?

[5-10 min]  Capacity Estimation
  • DAU, QPS, peak QPS
  • Storage (5-year horizon)
  • Bandwidth

[10-15 min]  High-Level Design
  • Draw: client → LB → servers → DB/cache
  • Identify core components
  • Describe data flow for main use case

[15-35 min]  Deep Dive
  • Scale each component
  • DB choice and schema sketch
  • Cache strategy
  • Handle failure cases

[35-45 min]  Identify Bottlenecks
  • Single points of failure
  • What breaks at 10× load?
  • Cost / operational complexity trade-offs

Design Principles to State Aloud
Start simple
  "I'll start with a monolith and extract services
   as we identify clear scaling boundaries."

State trade-offs explicitly
  "SQL gives us ACID but harder to shard;
   Cassandra gives us write scalability
   but eventual consistency. Given the
   requirements, I'll choose…"

Evolve incrementally
  V1: single DB + cache
  V2: read replicas
  V3: sharding
  V4: separate read/write models (CQRS)

Quantify everything
  "With 10K QPS and 1KB avg response,
   that's 10 MB/s bandwidth — well within
   a single 1Gbps link."
Red Flags to Avoid
  • Jumping to solution: always clarify requirements first — the interviewer may redirect you
  • Ignoring non-functional reqs: scale, latency, consistency matter as much as features
  • Single points of failure: every component should have redundancy or graceful degradation
  • No estimation: validate that your design can handle stated load
  • Over-engineering: don't add Kafka to a system with 100 QPS
  • Vague data model: sketch key tables/documents even at HLD stage
  • No trade-off discussion: every choice has a cost — say it
