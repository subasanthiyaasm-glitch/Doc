Four Pillars of OOP

The four pillars: Encapsulation (data hiding), Inheritance (code reuse), Polymorphism (flexible behavior), and Abstraction (hiding complexity). Core to Java design. W3Schools →
Pillars Overview
// 1. ENCAPSULATION — data hiding with getters/setters
class BankAccount {
  private double balance;

  public double getBalance() { return balance; }
  public void deposit(double amt) {
    if (amt > 0) balance += amt;
  }
}

// 2. INHERITANCE — code reuse via extends
class Animal {
  void eat() { System.out.println("Eating"); }
}
class Dog extends Animal {
  void bark() { System.out.println("Barking"); }
}

// 3. POLYMORPHISM — same method, different behavior
// Overloading (compile-time)
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }

// Overriding (runtime)
class Parent {
  void sound() { System.out.println("Generic"); }
}
class Child extends Parent {
  @Override
  void sound() { System.out.println("Specific"); }
}

// 4. ABSTRACTION — hide complexity
abstract class Shape {
  abstract double area();
  void display() { } // concrete OK
}
class Circle extends Shape {
  double radius;
  double area() { return Math.PI * radius * radius; }
}

// Interface — full abstraction
interface Drawable {
  void draw();
  default void print() { }  // Java 8+
}

class Rect implements Drawable {
  public void draw() { }
}

Encapsulation

Wrap data and methods into a single unit (class), restricting direct access. Use private fields with public getters/setters to control access and validate input. W3Schools →
BankAccount.java
class BankAccount {
  private double balance;  // hidden from outside
  private final String owner;

  BankAccount(String owner, double initial) {
    this.owner = owner;
    this.balance = Math.max(0, initial);
  }

  public double getBalance() { return balance; }
  public String getOwner() { return owner; }

  public void deposit(double amount) {
    if (amount <= 0) throw new IllegalArgumentException(
      "Amount must be positive");
    balance += amount;
  }

  public boolean withdraw(double amount) {
    if (amount > balance || amount <= 0) return false;
    balance -= amount;
    return true;
  }
}

Inheritance

IS-A relationship — subclass reuses and extends superclass behavior. Use extends for classes, implements for interfaces. Java supports single class inheritance only. W3Schools →
Inheritance.java
// Single Inheritance
class Animal {
  String name;
  Animal() { this("Unknown"); }
  Animal(String name) { this.name = name; }
  void eat() { System.out.println(name + " eats"); }
}

class Dog extends Animal {
  Dog(String name) { super(name); }  // must be first line
  void bark() { System.out.println("Woof!"); }
}

// Multilevel Inheritance
class Animal { }
class Mammal extends Animal { }
class Dog extends Mammal { }

// Multiple Inheritance via Interfaces
interface Flyable {
  void fly();
}
interface Swimmable {
  void swim();
}
class Duck extends Animal implements Flyable, Swimmable {
  public void fly()  { System.out.println("Flying"); }
  public void swim() { System.out.println("Swimming"); }
}
▶ Inheritance Types
Types
Single — A → B
Multilevel — A → B → C
Hierarchical — A → B, A → C
Multiple — via interfaces only
super Keyword
super() — call parent constructor
super.method() — call parent method
super.field — access parent field
Rules
No multiple class inheritance (diamond problem)
All constructors call super() implicitly
Object is root of all class hierarchies

Polymorphism

Same interface, different behavior. Compile-time (method overloading) resolved at compile time. Runtime (method overriding) resolved via dynamic dispatch at runtime. W3Schools →
Polymorphism.java
// ── Compile-time: Method Overloading ──
// Same method name, different parameter lists
class Calculator {
  int add(int a, int b)       { return a + b; }
  double add(double a, double b) { return a + b; }
  int add(int a, int b, int c)  { return a + b + c; }
}

// ── Runtime: Method Overriding ──
class Animal {
  void sound() {
    System.out.println("Generic sound");
  }
}

class Dog extends Animal {
  @Override
  void sound() {
    System.out.println("Bark");
  }
}

class Cat extends Animal {
  @Override
  void sound() {
    System.out.println("Meow");
  }
}

// Dynamic Method Dispatch
Animal a = new Dog();   // reference = Animal, object = Dog
a.sound();              // prints "Bark" — JVM resolves at runtime

Animal[] pets = {
  new Dog(), new Cat(), new Dog()
};
for (Animal p : pets) {
  p.sound();  // each calls its own overridden version
}
▶ Dynamic Dispatch
Overloading (compile-time)
Same name, different params
Resolved at compile time
Can have different return types
Overriding (runtime)
Same name, same params
Resolved at runtime (JVM)
Return type must be covariant
@Override annotation recommended
Key Rule
JVM dispatches on object type,
not reference type
Animal a = new Dog();
a.sound() → "Bark" (not "Generic")

Abstraction

Abstract classes provide partial implementation (can have state). Interfaces define a full contract (no state since Java 8 default methods). Use abstract class for "how partially", interface for "what". W3Schools →
Abstraction.java
// Abstract Class — partial implementation
abstract class Shape {
  String color;

  Shape(String color) { this.color = color; }

  abstract double area();  // must override

  void display() {         // concrete method OK
    System.out.println(color + " shape, area=" + area());
  }
}

class Circle extends Shape {
  double radius;
  Circle(String c, double r) { super(c); radius = r; }
  double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
  double w, h;
  Rectangle(String c, double w, double h) {
    super(c); this.w = w; this.h = h;
  }
  double area() { return w * h; }
}

// Cannot instantiate abstract class:
// Shape s = new Shape("red"); // COMPILE ERROR

// Interface — full abstraction
interface Drawable {
  void draw();  // abstract by default
}

interface Resizable {
  void resize(double factor);
}

class Canvas extends Shape implements Drawable, Resizable {
  Canvas(String c) { super(c); }
  double area() { return 0; }
  public void draw() { }
  public void resize(double f) { }
}
▶ Abstract vs Interface
Abstract Class
Can have constructors
Can have instance fields (state)
Can have concrete methods
Single inheritance only
Use when classes share common state
Interface
No constructors
Constants only (public static final)
Default methods since Java 8
Multiple interfaces allowed
Use when defining a capability

Interfaces

An interface defines a contract that classes must fulfill. Supports default methods (Java 8+), static methods, and functional interfaces for lambdas. W3Schools →
Interfaces.java
// Basic interface
interface Vehicle {
  void start();   // abstract by default
  int MAX_SPEED = 200;  // public static final
}

// Default method (Java 8+)
interface Printable {
  void print();

  default void prettyPrint() {
    System.out.println("=== " + toString() + " ===");
  }
}

// Functional interface (one abstract method → lambda)
@FunctionalInterface
interface Transformer<T> {
  T transform(T input);
}

// Implementing multiple interfaces
class Car implements Vehicle, Printable {
  public void start() {
    System.out.println("Car started");
  }
  public void print() {
    System.out.println("Car");
  }
}

// Lambda with functional interface
Transformer<String> upper =
  s -> s.toUpperCase();
upper.transform("hello");  // "HELLO"

// Diamond problem resolution
interface A {
  default void greet() {
    System.out.println("Hello from A");
  }
}
interface B {
  default void greet() {
    System.out.println("Hello from B");
  }
}
class C implements A, B {
  public void greet() {
    A.super.greet();  // must resolve explicitly
  }
}
▶ Interface Features
Java 8+ Additions
default methods — provide body
static methods — utility functions
Java 9+ Additions
private methods — helper for defaults
Key Rules
All methods are public by default
Fields are public static final
No constructors, no instance state
Class can implement multiple interfaces
Diamond conflict: must override explicitly

Composition

HAS-A relationship — build complex objects by composing simpler ones. Favor composition over inheritance for greater flexibility and avoid tight coupling. W3Schools →
Composition.java
// Composition: Car HAS-A Engine
class Engine {
  private int horsepower;

  Engine(int hp) { this.horsepower = hp; }

  void start() {
    System.out.println(horsepower + "hp engine started");
  }

  int getHorsepower() { return horsepower; }
}

class Car {
  private final Engine engine;  // HAS-A
  private String model;

  Car(String model, int hp) {
    this.model = model;
    this.engine = new Engine(hp);  // owns engine
  }

  void start() {
    System.out.println(model + ": ");
    engine.start();  // delegate to composed object
  }

  // Delegation pattern
  int getPower() { return engine.getHorsepower(); }
}

// Composition vs Inheritance
// ── Inheritance (IS-A): rigid ──
class Stack extends ArrayList<Object> {
  public void push(Object item) { add(item); }
  public Object pop() {
    return remove(size() - 1);
  }
}
// Problem: inherits get(), indexOf(), etc.
// Violates Stack contract

// ── Composition (HAS-A): flexible ──
class BetterStack<T> {
  private List<T> list = new ArrayList<>();

  public void push(T item) { list.add(item); }
  public T pop() {
    return list.remove(list.size() - 1);
  }
  public int size() { return list.size(); }
}
// Only exposes stack operations
▶ Composition vs Inheritance
Inheritance (IS-A)
Compile-time binding
Tight coupling to parent
Exposes full parent API
Fragile: parent changes break child
Composition (HAS-A)
Runtime binding (swap implementations)
Loose coupling via interfaces
Only exposes chosen methods
Robust: internal changes don't propagate
Rule of Thumb
Use inheritance for true IS-A
Use composition for HAS-A or "uses"
When in doubt, choose composition

SOLID Principles

Five design principles for maintainable, scalable OOP code. Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. W3Schools →
SOLID.java
// S — Single Responsibility Principle
// A class should have only ONE reason to change
class User {
  String name, email;
}

class UserRepository {         // persistence
  void save(User u) { }
}

class EmailService {           // notification
  void send(User u, String msg) { }
}

// O — Open/Closed Principle
// Open for extension, closed for modification
interface Discount {
  double apply(double price);
}
class NoDiscount implements Discount {
  public double apply(double p) { return p; }
}
class PercentDiscount implements Discount {
  double pct;
  PercentDiscount(double p) { pct = p; }
  public double apply(double price) {
    return price * (1 - pct);
  }
}
// Add new discount by adding a class — no changes to existing code

// L — Liskov Substitution Principle
// Subtypes must be substitutable for base types
class Bird {
  void fly() { System.out.println("Flying"); }
}
class Penguin extends Bird {
  @Override
  void fly() {
    throw new UnsupportedOperationException();
    // Violates LSP! Penguin breaks client expectations
  }
}
// Fix: separate Flyable interface from non-flying birds

// I — Interface Segregation Principle
// Clients shouldn't depend on methods they don't use
interface Workable {
  void work();
}
interface Feedable {
  void eat();
}
class Robot implements Workable {
  public void work() { }
}
class Human implements Workable, Feedable {
  public void work() { }
  public void eat()  { }
}

// D — Dependency Inversion Principle
// Depend on abstractions, not concretions
interface Database {
  void query(String sql);
}
class MySQL implements Database {
  public void query(String sql) { }
}
class Service {
  private final Database db;  // depends on interface
  Service(Database db) { this.db = db; }
}
// Swap MySQL for Postgres — Service unchanged
▶ SOLID Summary
S — Single Responsibility
One class → one job
O — Open/Closed
Extend via interfaces, don't modify
L — Liskov Substitution
Subclasses must honor parent contract
I — Interface Segregation
Many small interfaces > one fat one
D — Dependency Inversion
Depend on abstractions, inject deps
