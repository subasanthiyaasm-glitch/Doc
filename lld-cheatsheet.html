Low-Level Design, visually

LLD is about shaping the small building blocks of a program — classes — and deciding how they connect. Tap a step to walk through the basics one idea at a time.

Foundational

OOP — The Four Pillars

Encapsulation

Bundle data and the methods that operate on it. Hide internal state; expose only a public API. Use private fields + getters/setters.

Abstraction

Expose what an object does, hide how. Implemented via abstract class or interface. Callers depend on the contract, not the impl.

Inheritance

A child class reuses parent behaviour (extends). Avoid deep chains (>2 levels). Prefer composition when the "is-a" relationship is forced.

Polymorphism

One interface, many forms. Compile-time: method overloading. Runtime: method overriding via @Override + dynamic dispatch.

Encapsulation — keep fields private; control access through methods.
Encapsulation.java
public class BankAccount {
  private double balance;    // hidden state

  public void deposit(double amount) {
    if (amount > 0) balance += amount;
  }

  public double getBalance() { return balance; }
  // no public setBalance — prevents illegal direct write
}
Key Rules
Fields → private
Read access → getX()
Write access → validated setX()
Invariants enforced in setters
Never expose mutable internal collections directly
Abstraction — callers depend on the interface, not the concrete class.
Abstraction.java
interface Shape {
  double area();        // contract — no impl
  double perimeter();
}

class Circle implements Shape {
  private final double r;
  Circle(double r) { this.r = r; }

  @Override public double area() { return Math.PI * r * r; }
  @Override public double perimeter() { return 2 * Math.PI * r; }
}

class Rectangle implements Shape {
  private final double w, h;
  Rectangle(double w, double h) { this.w=w; this.h=h; }

  @Override public double area() { return w * h; }
  @Override public double perimeter() { return 2 * (w + h); }
}
interface vs abstract class
interface
Multiple inheritance OK
All methods implicitly public
No state (except constants)
abstract class
Single inheritance only
Can have state & concrete methods
Use when sharing default logic
Polymorphism — overloading (compile-time) vs overriding (runtime).
Polymorphism.java
// ── Compile-time: overloading ──
class Printer {
  void print(String s)  { System.out.println(s); }
  void print(int n)     { System.out.println(n); }
  void print(double d)  { System.out.println(d); }
}

// ── Runtime: overriding ──
abstract class Animal {
  abstract void speak();
}
class Dog extends Animal {
  @Override void speak() { System.out.println("Woof"); }
}
class Cat extends Animal {
  @Override void speak() { System.out.println("Meow"); }
}

// caller doesn't know which subtype
Animal a = new Dog();
a.speak();  // "Woof" — decided at runtime
When to use each
Overloading
Same operation, different input types
Resolved by compiler
Overriding
Subtype changes parent behaviour
Resolved at runtime (JVM vtable)
Always annotate @Override
Principles

SOLID Principles

S — Single Responsibility: a class should have exactly one reason to change.
SRP.java
// ✗ BAD — one class does too much
class UserService {
  void saveUser(User u)   { /* DB logic */ }
  void sendEmail(User u)  { /* Email logic */ }
  void generatePDF(User u){ /* Report logic */ }
}

// ✓ GOOD — each class has one job
class UserRepository  { void save(User u)  {} }
class EmailService    { void send(User u)  {} }
class ReportGenerator { void pdf(User u)   {} }
Why it matters
Smaller classes = easier tests
Change DB logic → only touch Repository
Change email format → only touch EmailService
Smell: class with >1 section of "why would this change?"
O — Open/Closed: open for extension, closed for modification.
OCP.java
// ✗ BAD — adding a shape requires editing this class
class AreaCalc {
  double area(Object shape) {
    if (shape instanceof Circle) { /* ... */ }
    else if (shape instanceof Rect) { /* ... */ }
    // adding Triangle means editing here ← bad
  }
}

// ✓ GOOD — add a shape by implementing the interface
interface Shape { double area(); }

class Circle   implements Shape { public double area() {/**/} }
class Rect     implements Shape { public double area() {/**/} }
class Triangle implements Shape { public double area() {/**/} }
// AreaCalc never changes — zero risk of regression
Pattern link
OCP is achieved via:
→ Strategy (swap algorithms)
→ Template Method (override steps)
→ Decorator (add behaviour)
Smell: long if-else/switch on type tags
L — Liskov Substitution: subtypes must be substitutable for their base type without breaking callers.
LSP.java
// ✗ VIOLATION — Square breaks Rectangle's contract
class Rectangle {
  protected int w, h;
  void setWidth(int w)  { this.w = w; }
  void setHeight(int h) { this.h = h; }
  int  area() { return w * h; }
}
class Square extends Rectangle {
  // forces both sides equal — breaks caller assumptions
  @Override void setWidth(int w)  { this.w = this.h = w; }
  @Override void setHeight(int h) { this.w = this.h = h; }
}

// ✓ FIX — separate abstractions, no shared hierarchy
interface Shape { int area(); }
record Rect(int w, int h)    implements Shape { public int area(){return w*h;} }
record Square(int side)       implements Shape { public int area(){return side*side;} }
LSP Test
Ask: "can I replace every use of the parent with the child without tests failing?"
Preconditions → no stronger in subtype
Postconditions → no weaker in subtype
Invariants → preserved
Smell: subtype throws UnsupportedOperationException
I — Interface Segregation: clients should not be forced to depend on methods they don't use.
ISP.java
// ✗ FAT interface — Robot must implement eat()
interface Worker {
  void work();
  void eat();   // robots don't eat!
}

// ✓ SPLIT into focused interfaces
interface Workable { void work(); }
interface Eatable  { void eat(); }

class Human implements Workable, Eatable {
  public void work() { /* work */ }
  public void eat()  { /* eat */ }
}
class Robot implements Workable {
  public void work() { /* work */ }
  // no eat() — clean!
}
Rule of thumb
Role interfaces > header interfaces
One interface per capability
Compose small interfaces as needed
Smell: empty/throw impls in a class that "implements X but not Y"
D — Dependency Inversion: depend on abstractions, not concretions. High-level modules should not import low-level modules.
DIP.java
// ✗ BAD — high-level depends on concrete low-level
class OrderService {
  private MySQLOrderRepo repo = new MySQLOrderRepo();
  // switching to Postgres = edit OrderService ← bad
}

// ✓ GOOD — depend on abstraction; inject the impl
interface OrderRepo { void save(Order o); }

class MySQLOrderRepo    implements OrderRepo { /**/ }
class PostgresOrderRepo implements OrderRepo { /**/ }

class OrderService {
  private final OrderRepo repo;
  OrderService(OrderRepo repo) { this.repo = repo; } // DI
  void placeOrder(Order o) { repo.save(o); }
}
Injection types
Constructor (preferred)
Deps explicit; immutable; testable
Setter injection
Optional deps; allows re-injection
Field injection (avoid)
Hidden deps; hard to test
Relationships

Class Relationships

Four ways classes relate: association, aggregation, composition, and inheritance. Choosing wrong causes brittle designs.
Relationships.java
// 1. Association — "uses" (loose coupling)
class Doctor  { void treat(Patient p) {} }  // no ownership

// 2. Aggregation — "has-a" (weak ownership, child survives)
class Department {
  List<Employee> employees;  // employees exist without dept
}

// 3. Composition — "has-a" (strong ownership, child dies with parent)
class House {
  private final Room room = new Room(); // Room can't exist alone
}

// 4. Inheritance — "is-a"
class Dog extends Animal {}    // Dog IS-A Animal

// 5. Realization / Implementation
class Circle implements Shape {} // Circle fulfils Shape contract
UML Arrows
Association A ──────→ B
Aggregation A ◇──────→ B
Composition A ◆──────→ B
Inheritance A ────▷ B
Realization A ·····▷ B
Prefer composition over inheritance. Inheritance is a tight coupling; favour composing behaviours via interfaces.
Aggregation vs Composition: if child objects make sense without the parent, it's aggregation. Otherwise composition.
"is-a" test: only use inheritance when the subtype truly satisfies LSP for all parent behaviour.
Clean Code

Clean Code Principles

DRY — Don't Repeat Yourself

Every piece of knowledge must have a single, unambiguous representation. Duplication = two places to update when logic changes.

KISS — Keep It Simple

Prefer simple solutions. Complexity is a liability. A junior should understand your code without explanation.

YAGNI — You Ain't Gonna Need It

Don't add functionality until it's required. Speculative generality increases complexity without proven benefit.

Law of Demeter

A method should call only: itself, its params, objects it creates, its direct fields. Never call a method on an object returned by another method (a.getB().getC() = violation).

Favour Immutability

Immutable objects are thread-safe by default and easier to reason about. Use final fields, records, and unmodifiable collections.

Tell, Don't Ask

Tell objects what to do, don't query their state and decide for them. Keeps logic inside the object that owns the data.

Naming & method size — names should reveal intent; methods should do one thing.
CleanCode.java
// ✗ BAD naming
int d;
boolean chk(User u) { return u.age >= 18; }

// ✓ GOOD naming
int elapsedDays;
boolean isAdult(User user) { return user.getAge() >= 18; }

// ✗ BAD — method does too many things
void processOrder(Order o) {
  // 80 lines of validation + discount + save + email
}

// ✓ GOOD — composed of small focused methods
void processOrder(Order o) {
  validate(o);
  applyDiscounts(o);
  orderRepo.save(o);
  emailService.sendConfirmation(o);
}

// Law of Demeter — ✗ train wreck
user.getAddress().getCity().getName();

// ✓ ask user directly
user.getCityName();
Quick Rules
Function lines → < 20
Parameters → ≤ 3 (use object if more)
Avoid boolean flags as params
No magic numbers → named constants
No comments for obvious code
Comments explain why, not what
Fail fast → validate at boundaries
Return early to reduce nesting

Creational Patterns controls object creation

Singleton — ensure a class has only one instance; provide a global access point.
Singleton.java
public class DatabasePool {
  // Initialization-on-demand holder — thread-safe, lazy
  private static class Holder {
    static final DatabasePool INSTANCE = new DatabasePool();
  }
  private DatabasePool() {}   // prevent external instantiation
  public static DatabasePool getInstance() {
    return Holder.INSTANCE;
  }

  // Enum singleton — simplest, serialization-safe
  public enum Config {
    INSTANCE;
    public String getUrl() { return System.getenv("DB_URL"); }
  }
}
When to use / avoid
Use for:
Shared resource pools (DB, thread pool)
Config / logger instances
Registry / cache managers
Avoid when:
Global state makes testing hard
Multiple instances needed in tests
Prefer DI container over manual singleton
Factory Method — define an interface for creating objects, but let subclasses decide which class to instantiate.
FactoryMethod.java
interface Notification { void send(String msg); }

class EmailNotif  implements Notification { public void send(String m){/*email*/} }
class SMSNotif    implements Notification { public void send(String m){/*sms*/} }
class PushNotif   implements Notification { public void send(String m){/*push*/} }

// Factory — creation logic centralised
class NotificationFactory {
  static Notification create(String type) {
    return switch (type) {
      case "email" -> new EmailNotif();
      case "sms"   -> new SMSNotif();
      case "push"  -> new PushNotif();
      default -> throw new IllegalArgumentException(type);
    };
  }
}
// usage
Notification n = NotificationFactory.create("email");
n.send("Welcome!");

Simple Factory
Static method; not a GoF pattern, but common
Factory Method (GoF)
Abstract creator with abstract create(); subclasses override
Abstract Factory
Family of related factories (e.g. UI theme: Light/Dark)
Builder — construct complex objects step-by-step; separate construction from representation.
Builder.java
class HttpRequest {
  private final String  url, method;
  private final Map<String,String> headers;
  private final String  body;
  private final int    timeout;

  private HttpRequest(Builder b) {
    url=b.url; method=b.method; headers=b.headers;
    body=b.body; timeout=b.timeout;
  }

  static class Builder {
    private final String url;
    private String  method  = "GET";
    private Map<String,String> headers = new HashMap<>();
    private String  body    = "";
    private int    timeout = 30;

    Builder(String url) { this.url = url; }
    Builder method(String m)  { method=m;  return this; }
    Builder header(String k, String v) { headers.put(k,v); return this; }
    Builder body(String b)    { body=b;    return this; }
    Builder timeout(int t)   { timeout=t; return this; }
    HttpRequest build()      { return new HttpRequest(this); }
  }
}
// usage
HttpRequest req = new HttpRequest.Builder("https://api.example.com")
    .method("POST")
    .header("Content-Type", "application/json")
    .body("{\"key\":\"val\"}")
    .timeout(60)
    .build();

≥4 constructor params
Many optional parameters
Need to validate before construction
Immutable object required
Lombok shortcut:
@Builder on the class
Java 16+ records:
Use record for truly simple immutables
Prototype — clone an existing object instead of creating a new one from scratch.
Prototype.java
abstract class Shape implements Cloneable {
  int x, y;
  abstract Shape clone();
}

class Circle extends Shape {
  int radius;
  Circle(Circle src) { // copy constructor
    this.x=src.x; this.y=src.y; this.radius=src.radius;
  }
  @Override public Circle clone() { return new Circle(this); }
}

// usage — cheap copy of expensive-to-create object
Circle original = new Circle();
original.radius = 10;
Circle copy = original.clone();
copy.radius = 20;  // original unaffected
Use cases
Object creation is costly (DB/network)
Need many similar objects with small diffs
Game entities, document templates
Deep vs Shallow copy:
Shallow: copies references (fast, risky)
Deep: copies referenced objects too (safe)
Design Patterns

Structural Patterns how classes are composed

Adapter — convert an incompatible interface into one the client expects. "Wrapper" pattern.
Adapter.java
// Target interface the client expects
interface MediaPlayer { void play(String file); }

// Incompatible 3rd-party library
class VLCPlayer {
  void playVLC(String file) { System.out.println("VLC: " + file); }
}

// Adapter bridges the gap
class VLCAdapter implements MediaPlayer {
  private final VLCPlayer vlc = new VLCPlayer();
  @Override
  public void play(String file) { vlc.playVLC(file); }
}

// Client uses target interface — unaware of VLC
MediaPlayer player = new VLCAdapter();
player.play("movie.avi");
Real-world examples
Java I/O: InputStreamReader adapts InputStream → Reader
JDBC: each DB driver adapts to JDBC API
SDK wrappers around third-party APIs
Object Adapter — wraps via composition (preferred)
Class Adapter — wraps via multiple inheritance (Java: impossible, use object adapter)
Decorator — attach additional responsibilities to an object dynamically without subclassing.
Decorator.java
interface Coffee { double cost(); String desc(); }

class Espresso implements Coffee {
  public double cost() { return 1.5; }
  public String desc() { return "Espresso"; }
}

// Base decorator
abstract class CoffeeDecorator implements Coffee {
  protected final Coffee wrapped;
  CoffeeDecorator(Coffee c) { wrapped = c; }
}

class MilkDecorator extends CoffeeDecorator {
  MilkDecorator(Coffee c) { super(c); }
  public double cost() { return wrapped.cost() + 0.3; }
  public String desc() { return wrapped.desc() + ", Milk"; }
}

// Build at runtime: Espresso + Milk + Vanilla
Coffee c = new VanillaDecorator(new MilkDecorator(new Espresso()));
System.out.println(c.desc() + " $" + c.cost()); // $1.9
Java stdlib examples
BufferedReader(new FileReader(f))
Collections.unmodifiableList(list)
Collections.synchronizedList(list)
vs Inheritance:
Inheritance = static; fixed at compile time
Decorator = dynamic; composed at runtime
Avoids class explosion (2^n combinations)
Facade — provide a simplified interface to a complex subsystem.
Facade.java
// Complex subsystem classes
class CPU       { void freeze(){} void jump(long pos){} void execute(){} }
class Memory    { void load(long pos, byte[] data){} }
class HardDisk  { byte[] read(long lba, int size){ return null; } }

// Facade — one easy method for clients
class ComputerFacade {
  private final CPU cpu = new CPU();
  private final Memory mem = new Memory();
  private final HardDisk hdd = new HardDisk();

  void start() {
    cpu.freeze();
    mem.load(0, hdd.read(0, 1024));
    cpu.jump(0);
    cpu.execute();
  }
}

// Client — one call, no knowledge of subsystem
new ComputerFacade().start();

Proxy — a surrogate that controls access to the real object; adds lazy loading, caching, or access control.
Proxy.java
interface Image { void display(); }

class RealImage implements Image {
  private final String file;
  RealImage(String file) {
    this.file = file;
    loadFromDisk();   // expensive!
  }
  private void loadFromDisk() { System.out.println("Loading: " + file); }
  public void display()      { System.out.println("Display: " + file); }
}

// Lazy proxy — defers expensive load until first display()
class ProxyImage implements Image {
  private RealImage real;
  private final String file;
  ProxyImage(String file) { this.file = file; }
  public void display() {
    if (real == null) real = new RealImage(file);
    real.display();
  }
}

Virtual Proxy — lazy init expensive object

Remote Proxy — represents remote object (RMI)
Caching Proxy — cache results of operations
Logging Proxy — log calls transparently

Composite — compose objects into tree structures; treat individual objects and compositions uniformly.
Composite.java
interface FileSystem { void show(String indent); }

class File implements FileSystem {        // Leaf
  private final String name;
  File(String name) { this.name = name; }
  public void show(String indent) { System.out.println(indent + name); }
}

class Directory implements FileSystem {  // Composite
  private final String name;
  private final List<FileSystem> children = new ArrayList<>();

  Directory(String name) { this.name = name; }
  void add(FileSystem fs) { children.add(fs); }

  public void show(String indent) {
    System.out.println(indent + name + "/");
    children.forEach(c -> c.show(indent + "  "));
  }
}
When to use
Tree structures (file systems, UI components, org charts)
Client should treat leaf and container the same way
Real examples:
Swing: JPanel contains JButtons and more JPanels
XML/HTML DOM tree
File system directories
Design Patterns

Behavioral Patterns how objects communicate

Observer — when one object changes state, all its dependents are notified automatically.
Observer.java
interface Observer   { void update(String event); }
interface Observable {
  void subscribe(Observer o);
  void unsubscribe(Observer o);
  void notifyAll(String event);
}

class StockMarket implements Observable {
  private final List<Observer> observers = new ArrayList<>();
  private double price;

  void setPrice(double p) {
    price = p;
    notifyAll("PRICE_CHANGE:" + p);
  }
  public void subscribe(Observer o)   { observers.add(o); }
  public void unsubscribe(Observer o) { observers.remove(o); }
  public void notifyAll(String e)    { observers.forEach(o -> o.update(e)); }
}

class Trader implements Observer {
  public void update(String e) { System.out.println("Trader: " + e); }
}

Push — subject sends full data in event

Strategy — define a family of algorithms, encapsulate each, and make them interchangeable at runtime.
Strategy.java
interface SortStrategy { void sort(int[] arr); }

class BubbleSort implements SortStrategy {
  public void sort(int[] arr) { /* bubble sort */ }
}
class QuickSort  implements SortStrategy {
  public void sort(int[] arr) { /* quick sort */ }
}

class Sorter {
  private SortStrategy strategy;
  void setStrategy(SortStrategy s) { strategy = s; }
  void sort(int[] arr) { strategy.sort(arr); }
}

// Switch algorithms without touching Sorter
Sorter sorter = new Sorter();
sorter.setStrategy(new QuickSort());
sorter.sort(data);
sorter.setStrategy(arr.length < 10 ? new BubbleSort() : new QuickSort());

Command — encapsulate a request as an object; supports undo/redo, queuing, and logging.
Command.java
interface Command { void execute(); void undo(); }

class TextEditor {
  private StringBuilder text = new StringBuilder();
  void write(String s)   { text.append(s); }
  void delete(int n)    { text.delete(text.length()-n, text.length()); }
  String getText()      { return text.toString(); }
}

class WriteCommand implements Command {
  private final TextEditor editor; private final String text;
  WriteCommand(TextEditor e, String t) { editor=e; text=t; }
  public void execute() { editor.write(text); }
  public void undo()    { editor.delete(text.length()); }
}

class CommandHistory {
  private final Deque<Command> history = new ArrayDeque<>();
  void execute(Command cmd) { cmd.execute(); history.push(cmd); }
  void undo()              { if (!history.isEmpty()) history.pop().undo(); }
}
Use cases
Text editors (Ctrl+Z undo)
Transaction scripts
Task queues / job schedulers
GUI button actions
Macro recording
Key roles: Invoker → Command → Receiver
State — allow an object to change its behaviour when its internal state changes; eliminates large if-else chains.

Template Method — define the skeleton of an algorithm in a base class; let subclasses fill in the steps.
TemplateMethod.java
abstract class DataMigration {
  // Template method — fixed algorithm skeleton
  final void migrate() {
    extractData();      // step 1
    transformData();    // step 2
    loadData();         // step 3
    sendReport();       // step 4 — concrete (shared)

  abstract void extractData();
  abstract void transformData();
  abstract void loadData();

  void sendReport() { System.out.println("Migration done"); } // hook

class CSVMigration extends DataMigration {
  void extractData()   { /* read CSV */ }
  void transformData() { /* map fields */ }

}

Chain of Responsibility — pass a request along a chain of handlers; each decides to handle or pass it on.
ChainOfResponsibility.java
abstract class AuthHandler {
  protected AuthHandler next;
  AuthHandler setNext(AuthHandler n) { next=n; return n; }
  abstract void handle(Request req);
}

class RateLimitHandler extends AuthHandler {
  public void handle(Request req) {
    if (req.isRateLimited()) { System.out.println("429 Too Many Requests"); return; }
    if (next != null) next.handle(req);
  }
}
class AuthTokenHandler extends AuthHandler {
  public void handle(Request req) {
    if (!req.hasValidToken()) { System.out.println("401 Unauthorized"); return; }
    if (next != null) next.handle(req);
  }
}

// Chain: RateLimit → AuthToken → Controller
AuthHandler chain = new RateLimitHandler();
chain.setNext(new AuthTokenHandler()).setNext(new ControllerHandler());

Other important behavioral patterns at a glance.
Iterator.java
// Iterator — sequential access without exposing internals
interface Iterator<T> { boolean hasNext(); T next(); }

class NumberRange implements Iterable<Integer> {
  private final int start, end;
  NumberRange(int s, int e) { start=s; end=e; }
  public Iterator<Integer> iterator() {
    return new Iterator<>() {
      int cur = start;
      public boolean hasNext() { return cur <= end; }
      public Integer next()    { return cur++; }
    };
  }
}
// for-each works on any Iterable
for (int n : new NumberRange(1, 5)) System.out.println(n);
Mediator.java
// Mediator — centralise communication
// between objects so they don't reference
// each other directly (chat room model)

interface Mediator {
  void send(String msg, Colleague from);
}

class ChatRoom implements Mediator {
  private List<Colleague> members = new ArrayList<>();
  void join(Colleague c) { members.add(c); }
  public void send(String msg, Colleague from) {
    members.stream()
      .filter(m -> m != from)
      .forEach(m -> m.receive(msg));
  }
}

Class diagram notation — the core of every LLD interview.
Class Diagram Notation
┌──────────────────────────────┐
│       <<interface>>          │
│          Shape               │
├──────────────────────────────┤
│ + area(): double             │  <-- + public
│ + perimeter(): double        │  <-- # protected
├──────────────────────────────┤  <-- - private
│ (no fields in interface)     │  <-- ~ package
└──────────────────────────────┘

┌──────────────────────────────┐
│           Circle             │  <- class name
├──────────────────────────────┤
│ - radius: double             │  <- fields
│ - colour: String             │
├──────────────────────────────┤
│ + area(): double             │  <- methods
│ + perimeter(): double        │
│ + setRadius(r: double): void │
└──────────────────────────────┘

Relationships in diagrams:
A ────────▷ B   inheritance (A extends B)
A ·········▷ B   realization (A implements B)
A ──────────→ B  association (A uses B)
A ◇──────────→ B aggregation (A has-a B, weak)
A ◆──────────→ B composition (A owns B, strong)
A ···········→ B dependency (A depends on B)

Multiplicity:
1     one          *    many
0..1  zero or one  1..* one or more

LLD System Design Problems

Classic interview problems — key classes and design decisions for each.

Parking Lot

  • Entities: ParkingLot, Floor, Slot, Vehicle, Ticket
  • Enums: SlotType (SMALL/MEDIUM/LARGE), VehicleType
  • Key methods: parkVehicle(), removeVehicle(), findNearestSlot()
  • Pattern: Strategy (slot assignment), Observer (capacity alerts)
  • Concurrency: lock slot before assigning to prevent race

Library Management System

  • Entities: Book, BookItem, Member, Librarian, Loan, Fine
  • Key methods: searchCatalog(), checkOut(), returnBook(), payFine()
  • Pattern: Singleton (catalog), Observer (reservation queue)
  • Relations: Book → many BookItems (copies); Member borrows BookItem

Elevator System

  • Entities: ElevatorController, Elevator, Floor, Request
  • Enums: Direction (UP/DOWN/IDLE), ElevatorState
  • Key methods: addRequest(), processNext(), move()
  • Pattern: State (elevator states), Strategy (scheduling: FCFS, SCAN/LOOK)

ATM Machine

  • Entities: ATM, Card, Account, CashDispenser, Keypad, Screen
  • States: Idle → CardInserted → PINEntered → SelectingTransaction → Dispensing
  • Pattern: State (ATM states), Singleton (ATM), Chain of Responsibility (auth checks)
  • Key: atomicity — debit account and dispense cash must succeed/fail together

Chess Game

  • Entities: Board, Cell, Piece, Player, Game, Move
  • Subclasses: King, Queen, Rook, Bishop, Knight, Pawn (all extend Piece)
  • Key methods: isValidMove(), movePiece(), isCheckmate()
  • Pattern: Command (move history/undo), Observer (game events)

Vending Machine

  • Entities: VendingMachine, Item, Inventory, Coin, Transaction
  • States: Idle → HasMoney → SelectionMade → Dispensing → Change
  • Pattern: State (machine states), Singleton (machine instance), Strategy (change dispensing)
  • Key: refund on cancel; exact change vs change dispensing logic

Ride Sharing (Uber/Ola)

  • Entities: Rider, Driver, Trip, Location, Payment, Rating
  • Key methods: requestRide(), matchDriver(), startTrip(), endTrip()
  • Pattern: Observer (driver location updates), Strategy (pricing, driver matching), Singleton (RideManager)

Hotel Booking

  • Entities: Hotel, Room, Booking, Guest, Payment, RoomType
  • States: Room — Available → Reserved → CheckedIn → Cleaning → Available
  • Key methods: searchRooms(dates, type), book(), checkIn(), checkOut()
  • Pattern: State (room), Factory (room types), Observer (availability)
LLD Interview Approach — a repeatable 5-step method for any design question.
Step-by-step method
1. CLARIFY REQUIREMENTS (2 min)
   - Functional: what does it do?
   - Non-functional: scale, concurrent users?
   - Constraints: no 3rd-party libs? specific language?

2. IDENTIFY ENTITIES (3 min)
   - Nouns from requirements → candidate classes
   - Group related attributes together
   - Distinguish entity vs value object vs enum

3. DEFINE RELATIONSHIPS (3 min)
   - Is-a (inheritance) or Has-a (composition)?
   - Multiplicities: 1:1, 1:N, M:N
   - Draw rough class diagram

4. CORE METHODS & FLOWS (5 min)
   - Key operations: what are the primary verbs?
   - Walk through a main scenario with sequence
   - Identify state transitions if applicable

5. APPLY PATTERNS (3 min)
   - Which patterns fit naturally?
   - Add extension points (OCP)
   - Mention concurrency concerns if relevant
Pattern Selection Guide
"only one instance" → Singleton
"create without specifying class" → Factory
"complex object step by step" → Builder
"notify many on change" → Observer
"swap algorithm at runtime" → Strategy
"object changes behaviour by state" → State
"add behaviour without subclass" → Decorator
"incompatible interface" → Adapter
"undo/redo" → Command
"pass request along chain" → Chain of Resp.
"simplify complex subsystem" → Facade
"tree of objects" → Composite
